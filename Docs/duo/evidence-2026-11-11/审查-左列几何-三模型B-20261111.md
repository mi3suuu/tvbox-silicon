## 0. 数据流追踪（stage → pictureColumn → OneSkinWindowGeometry）

```
VideoDetailView.oneSkinShape  ──(离散枚举: halfFold/fullBleed/split/column)──▶  OneSkinStage.shape
OneSkinGeometryDriver.geometry
    ├─ screenSize = OneSkin.fixedScreenSize()  // appWindowScene.screen.bounds（Duo 物理固定 951×669，不随方向交换）
    ├─ ratioBase = shape.isLandscape ? (长,短) : (短,长)          // 比例坐标乘法基准 = 物理全屏
    └─ box       = 同上，横持另扣 rightReserve 47                // 951−47=904
OneSkinStage.body:
    avail = stableBucket(availableSize(driver.box, screen), 8)   // 量化桶

    landscapeNow = effectiveShape.isLandscape（只认离散 shape，QA 开关覆盖）
    box = size（量化后的 avail）；ratio = ratioBase
    ├─ split:   colL = box.width×0.4735  gap×0.0612  colR×0.4654
    │           pictureColumn((colL, ratio.height), landscape: true,  ratioBase)
    ├─ column:  picH = pictureHeightOf(box) = min(boxH×0.091 + boxW/1.819 + boxH×0.04, boxH×0.72)
    │           pictureColumn((ratio.width, picH), landscape: false, ratioBase)
    │           └─ portraitTopInset = ratio.height × (colW<500 ? 0.0634 : 0.091)   ★已接线
    ├─ fullScreen / fullBleed(edgeToEdge) / halfFold：走铺满分支（fullScreen||edgeToEdge=true）

    geo = OneSkinWindowGeometry(size: colSize, landscape:, fullScreen: fs||edge, portraitTopInset:)   L2057–2085
pictureControls:  geo = OneSkinWindowGeometry(size:, landscape:, fullScreen: fs||edge)              L1941–1945
                  ⛔ 未传 portraitTopInset —— 与画面层不同源（缺陷 D1）
```

## 2. 专项疑点核验

### 2a. 横持 winH 是否仍用固定 1.819？真机播放态窗口比例是多少？

**是，仍固定。** `OneSkinWindowGeometryCore.swift:81` `windowAspect: CGFloat = 1.819`；横屏（L170）、竖屏（L200）、`pictureHeightOf`（L1922）三处全部用它。真机实测：

| 形态 | 真机窗口 | 真机比例 | 与 1.819 差 |
|---|---|---|---|
| 内屏竖持·播放态（9号） | 669×311.67 | **2.146** | +18%（窗口高多算 56pt） |
| 内屏竖持·选择态（16–18号） | 637×358 | **1.779**（16:9） | −2.3% |
| 外屏竖持（10/11号） | 350×258 | **1.357** | +34%（比例维度）/ 高度巧合差 −2pt |
| 内屏横持 | 无同页配对实测（定案 §8 明示未完成） | — | 需复验 |

**三个有实测的形态没有一个等于 1.819**。1.819 本身来自 Fig VM 2034×1398 的旧量测（pictureColumn 注释 L2020–2039），不是真机值。定案 §7 修复表第 3 行明确要求「windowAspect 1.819 固定 → **跟随片源**（实测 1.762≈16:9）」，该条**未落实**（见 2c）。

> 代码注释（L75–80）给出了不跟随片源的理由（兜底 ratio=0.4 会把 winH 算成 842pt、跳窗）。这个顾虑只对「用 presentationSize 直接算 winH 且未就绪」成立；定案要求的是跟随**版式**修正（每形态一个定案比例），与该顾虑不冲突，需产品裁决后改。

### 2b. 内屏竖持选择态（y=506）与播放态（y=85.67）两态在代码里怎么区分？

**没有区分，也没有实现选择态。**
- `OneSkinStage` 的 column 分支（L1733–1753）是唯一的竖持单列版式：`pictureColumn` 恒在顶部（winY≈87），`detailColumn` 在下。
- 状态量 `playing`（L696）传入后在 stage 体内**零消费**（仅 L977 注释提及已删除的旧逻辑）；`fullScreenNow`/`folded`/`effectiveShape` 都不是「播放/选择」维度。
- 真机选择态的三个结构性特征——视频窗口 y=506..864、x=16..653（**16pt 侧缩进**，与代码「外壳满宽」策略相反）、chip 行在**视频上方**（460..486）、底部常驻带（864..951）——代码中均无对应实现。
- 需复验项：真机两态究竟是**页面状态切换**还是**同一页滚动**（16/17/18 三张 y 完全一致且四边 0px 抖动，量测报告判为「布局常量决定」；但 14/15 详情态的视频/照片区在 y470 起，需同页滚动序列才能定论）。修复方案取决于该结论。

### 2c. 外屏 h=258（0.7371 竖视频）代码是否支持非 16:9 片源窗口（presentationSize 路径）？

**不支持。** presentationSize 链路已接但**到不了窗口几何**：
- `VideoDetailView.syncAspectFromPresentationSize()`（L2085–2103，`task(id: playerSession?.player.currentItem)`，40×150ms 轮询）→ `playerAspectRatio` → `OneSkinStage.aspectRatio`（L2983，经 `BiliAspectMode.effectiveAspect`）。链路本身符合「presentationSize 唯一真源」铁律。
- 但 `aspectRatio` 在 OneSkinStage 内只有两个消费者：① fullBleed/halfFold 的 `bleedingPictureHeight`（L1679/1790）；② `.stretch` 模式的 `OneSkinStretchModifier`（L426）。
- 窗口几何（column/split 分支的 winX/winY/winW/winH）**完全不读 playerAspect**——`OneSkinWindowGeometry` 构造参数里没有 aspect（pictureColumn L2060 注释明示「尺寸已与片源比例解耦」）。
- 结果：外屏竖持恒出 466×256 的 1.819 横窗，真机是 350×258 的 1.357「竖视频窗口」；片源为竖片时画面在 1.819 横窗内 letterbox 成一条，与真机的竖窗口形态根本不同。

## 3. Metrics.px() 覆盖检查（全部 win 赋值路径）

`OneSkinWindowGeometryCore.init` 三分支逐一核对：

| 分支 | winW | winH | winX | winY |
|---|---|---|---|---|
| fullScreen（含 edgeToEdge，L126–136） | `px(colW)` ✓ | `px(colH)` ✓ | 0（字面量）✓ | 0（字面量）✓ |
| landscape（L163–181） | `px(innerW)` ✓ | `px(fittedH)` ✓ | 0 ✓ | `px(clamp(…))` ✓ |
| portrait（L182–215） | `px(innerW)` ✓ | `px(min(wanted,limit))` ✓ | 0 ✓ | `px(min(top,…))` ✓ |

**全部覆盖，无漏网连续尺寸。** 归一化 accessor `x(_:)`/`y(_:)`（L221–222）不做 px 取整，但它们是派生坐标、不属于 win 赋值路径，Chrome 层再取整亦无抖动风险。`winH` 参与的 `self.winH` 先取整后用于 `winY` 夹逼（L215 用的是取整后的 `self.winH`）——同源自洽，无问题。**此项确认无误。**

## 4. onGeometryChange / GeometryReader / frozenBox 旋转动画旧方向风险（对照「Duo 内屏方向声明不可信」硬约束）

- **布局路径已无 GeometryReader / onGeometryChange 残留**：body 的几何输入 = `geoDriver.geometry.box`（L1145，离散快照），driver 只在「形态/折叠/遮挡/屏幕跨档」时 rebuild（三道幂等门）。全仓对这两个 API 的出现均为注释（历史教训记录），无实际调用。✓
- **frozenBox 已退化为死状态**：仅剩 DEBUG 日志消费（L1592），L1320/L1402 两处赋值无实际读者。它曾是旧方向风险源，现已不参与布局——风险解除，但注释与 @State 仍会误导维护者（D7）。
- **残余风险（D6，需真机复验）**：`VideoDetailView.landscapeScreen`（L1583–1601）的大屏校正路径读 **`appWindowScene.keyWindow.bounds`** 作为 `OneSkinShapeResolver.isLandscape` 的 `containerSize`，且 `wasPortrait` 传 `nil`（无滞回记忆）。该文件自己的注释承认「keyWindow.bounds 在旋转动画里每帧都在变」——旋转中间帧它既不是旧方向也不是新方向。若 declared 翻成 landscape 而 window.bounds 仍是竖值（669×951，h/w=1.42 > 1.15），isLandscape 返回 false → 中间帧误判成 fullBleed（竖持版式）后猛跳 split。这与硬约束「形态判据只能取实际空间宽高比、不得按方向信号交换宽高」只做到了一半：用了实际比例，但用的是**动画期的连续 keyWindow 值**而非稳定空间。滞回参数 `portraitExit=1.05` 因 `wasPortrait=nil` 永远走不到。
- driver 的 `onChange(of: OneSkin.fixedScreenSize())`（L1417）触发源是静态 screen.bounds——Duo 上不随方向交换，不会引入动画中间帧。✓

## 5. 缺陷清单（按严重度排序）

### D1（高）pictureControls 未传 portraitTopInset —— 控件层窗口顶边与画面层不一致
- **位置**：`App/OneSkin.swift:1941–1945`（对比画面层 L2057–2085）。
- **现状**：控件层 `OneSkinWindowGeometry(size:, landscape:, fullScreen:)` 未传 `portraitTopInset`，落入 `nil → colH × Metrics.portraitTop(0.091)` 回退分支（Core L209）。而 colH 是画面区高度（picH），不是屏高。
- **代码值 vs 真机**：内屏竖持控件层 winY = 491.45×0.091 = **44.8**，画面层 = 951×0.091 = **86.5**（真机 85.67）→ 控件整体**上移 42pt**；外屏控件层 = 344.21×0.091 = **31.3**，画面层 = **43.0**（真机 43.00）→ 上移 11.7pt。横屏/全屏/双列不受影响（portraitTopInset 只在竖屏分支生效）。
- **真机值**：OneSkinPlayerChrome 的顶/底栏按 `winY` 偏移定位（L341/445 `.offset(x: winX, y: winY)`），控件应与画面窗口同框。
- **修复建议**：`pictureControls` 增加与 pictureColumn 完全相同的 `portraitTopInset` 实参（同源传 `ratioBase.height × (colW<500 ? 0.0634 : 0.091)`），或把该 inset 计算提为两者共用的单一入口；避免 R10 式「改一处漏一处」复发。

### D2（高）windowAspect 固定 1.819 —— 内屏竖持播放态窗口高多算 18%
- **位置**：`Sources/TVCore/OneSkinWindowGeometryCore.swift:81`（常量）、`:170/:200`（横/竖分支）、`App/OneSkin.swift:1922`（pictureHeightOf）。
- **现状**：winH = winW/1.819。
- **代码值**：内屏竖持播放态 winH=368、窗口底 455。**真机值**：311.67、397.33（9号，像素实测高置信）。差 +56.3pt（+18%）；真机比例 2.146。
- **影响**：竖持播放态窗口下探 57pt，挤占 chip 行与标题区；与真机版式不符。
- **修复建议**：按定案 §7 改为「分形态版式比例」或跟随片源（需先裁决 2a 中代码注释给出的兜底顾虑；每形态一个常量即可绕开兜底 0.4 跳窗问题）。三形态真机值：竖持播放态 2.146、竖持选择态 1.779、外屏 1.357（横持待实测）。

### D3（高）内屏竖持「选择态」未实现 —— 无播放/选择两态区分
- **位置**：`App/OneSkin.swift:1733–1753`（column 分支）、`:696`（`playing` 参数零消费）。
- **现状**：竖持单列恒为「画面在顶（winY≈87 满宽 669）+ 详情在下」；chip 行 overlay 恒在画面下方（barBottom≈452.6 → chip y≈472..498）。
- **真机值**：选择态视频窗口 **x=16..653（w=637，16pt 侧缩进）、y=506..864（h=358，16:9）**；chip 行 y=460.3..486 在**视频上方**；底部常驻带 y=864..951（h=87，暖褐）。播放态则 y=85.67 起、满宽。
- **修复建议**：先真机复验两态切换机制（状态切换 vs 同页滚动，见 §2b），再决定是加 `playing` 分支（选择态：视频下移、16pt 侧缩进、chip 上置、底部带常驻）还是滚动锚定方案。代码中「外壳满宽」策略与真机选择态的 16pt 侧缩进直接冲突，需一并裁决。

### D4（高）外屏竖持窗口 winX/winW/winH 与真机不符（且不支持 1.357 竖视频窗口）
- **位置**：`Sources/TVCore/OneSkinWindowGeometryCore.swift:138–141/199`（竖屏满宽策略 + 1.819）、`App/OneSkin.swift:1748`（detailColumn 也按 ratio.width=466 铺）。
- **现状**：x=0、w=466、h=256（=466/1.819）。
- **真机值**：**x=16、w=350、h=258**（10/11号帧差实测；外屏量测报告 §2.2/§5：内容列 350pt、leading 16pt、右侧 100pt 非 App 内容）。
- **影响**：整页按 466 满宽排版会在真机外屏上横向错位（量测报告明示「按 466pt 满宽布局会错位 100pt」）；h 的 −2pt 只是巧合，比例（1.819 vs 1.357）根本不同。
- **修复建议**：外屏（<500pt 宽）分支引入 16pt 侧缩进与 350pt 内容列；窗口比例走 D2 的分形态常量。注意与「竖持外壳满宽」用户决策的冲突需显式裁决（真机 One 外屏不是满宽）。

### D5（中）内屏横持 winY/winH 无真机对照，现有实测与代码悬殊且证据互相冲突
- **位置**：`Sources/TVCore/OneSkinWindowGeometryCore.swift:163–181`。
- **现状**：winH=235（=428/1.819）、winY=182（centre 0.455）。
- **真机值**：定案 §8 明示「内屏横持视频矩形未完成项」；但 1号 Form A（`One真机量测-内屏竖持-20261111.md` §1）像素实测播放器面板 **y=111.33、h=366.33**（宽 467.67，与定案左列 428 冲突）。若 Form A 的纵向量测成立，代码 winH 差 −131pt、winY 差 +71pt。
- **修复建议**：先复测横持同页配对（播放/未播放帧差），拿左列宽与窗口矩形的自洽解；再决定 centre 0.455 与窗口比例。**在拿到新证据前不要动这两个数**。

### D6（中）landscapeScreen 大屏校正读动画期 keyWindow.bounds，滞回参数实际失效

## 6. 确认无误清单（代码路径已验证）

1. **横持三栏比例**：容器基准 0.4735/0.0612/0.4654 → 428.04/55.32/420.7，与定案实测 428/55.3/420.7 逐位吻合（和=904，无溢出）。
2. **竖持窗口顶比例分设备**（colW<500→0.0634，≥500→0.091）：已实现并接线到 pictureColumn（L2078–2084）；计算值 86.54（内屏）/42.98（外屏）vs 实测 85.67/43.00，偏差 ≤0.9pt。
3. **Metrics.px() 取整覆盖全部 win 赋值路径**（含 fullScreen/edgeToEdge 分支）；winX 恒 0 字面量；winY 夹逼使用取整后的 winH，同源自洽。
4. **布局路径无 GeometryReader/onGeometryChange**：几何输入 = geoDriver 离散快照 + 静态 screen.bounds，量化桶 8pt + 三道幂等门在位；旋转自反馈环的结构性风险已解除。
5. **窗口越界防护**：竖屏 `limit=colH×0.94−top`、`winY≤colH−winH`，横屏 `winY∈[0, usableH−fittedH]`，与 TVCore 单测矩阵（`OneSkinWindowGeometryTests`）一致；任意容器下窗口不出列。
6. **presentationSize→playerAspectRatio 链路**（task(id: currentItem) 轮询 + BiliAspectMode）符合「唯一真源」铁律；fullBleed/halfFold 的 picH 与 .stretch 模式正确消费。
7. **片源 letterbox 机制**：窗口恒定 + `.resizeAspect`/clipped，竖片不撑窗——与真机播放态「窗口内 letterbox」行为一致。
8. **底部胶囊条不画在 pictureColumn ZStack 内**（避开 UIKit 图层盖住），overlay-once 修复在位。
