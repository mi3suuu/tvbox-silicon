## 一、iphone-duo-skill · 核心原则

| # | 社区建议 | 映匣现状 | 证据 |
|---|---|---|---|
| 1.1 | **按 size class + 容器尺寸决定布局**，不按 `userInterfaceIdiom`、不按 orientation、不按 `UIScreen.main` | **已做（框架层）**，但**播放页例外**：`PlayerView` / `MobilePlayer` / `VideoDetailView` 仍按 `interfaceOrientation` 切横屏控制栏 | `App/RootView.swift:40-42`（读 sizeClass）、`:192` `PhoneTabs.inUse(horizontal:)`；反例见 `App/PlayerView.swift:755`、`App/VideoDetailView.swift:1064` |

## 二、iphone-duo-skill · 布局容器选择

| # | 社区建议 | 映匣现状 | 证据 |
|---|---|---|---|
| 2.1 | List→detail 用 `NavigationSplitView` / `UISplitViewController`，**内屏横屏才双栏**，竖屏折叠成单栏 | **不适用**：映匣是标签栏 App，没有 list→detail 主结构；播放页的「左右分栏」是**同页两栏（播放器 + 详情）**，属 2.2 而非 2.1 | — |
| 2.2 | 两个对等面板（player + queue、hero + shelf）用 `ArrangementView` + `.split` | **未做（有意）**：映匣用 **`AnyLayout` 单实例化**实现同一目的——「一套结构，只换轴向」。理由：`ArrangementView` 会**重建两个 pane**，而映匣的播放器必须**单实例**（`watchPlayer` 永远在 index 0），否则折叠/转向会销毁重建 AVPlayer 图层，触发 AVKit 误开画中画、`onDisappear` 提前 `release`。这是映匣踩过的坑，不是没读到文档 | `映匣功能清单.md` §2.3「播放页单实例化」+「关闭 AVKit 自动画中画」 |
| 2.3 | 前后景叠加（控件压在页面上）用 `ArrangementView` + `.overlay` | **不适用**：映匣的叠加层（浮动分区栏、mini player、选集抽屉）是**跨 section 的全局层**，不是页内两 pane | `App/RootView.swift:314` 附近 `videoMiniPlayer` overlay |
| 2.4 | 单列滚动内容**不需要**新容器，只要封顶宽度 | **已做** | 同 1.4 |
| 2.5 | 网格按**实测宽度**算列数，**四舍五入**，有折叠时优先偶数 | **未做**：`Layout.cardColumns` 是常量列数，未按容器宽算 | `App/RootView.swift` 引用处 `Layout.cardColumns`（DesignSystem 内定义） |

### ArrangementView 七条 trap —— 映匣为什么基本不适用

| trap | 映匣是否踩 | 说明 |
|---|---|---|
| 1. size preference 要挂在 pane 不是容器 | 不适用 | 未用 ArrangementView |
| 2. 一边给 idealWidth，另一边必须有 minWidth | 不适用 | 同上 |
| 3. minWidth 装不进半个屏 → **整个 arrangement 渲染空白** | **概念同源（已修）** | 映匣白屏是另一种「条件不成立 → 返回空视图」，见 `Duo适配报告.md` §一 |
| 4. `.axes(.horizontal)` 在竖容器只显示主 pane，副 pane 消失 | 不适用 | 同上 |
| 5. 别把 ArrangementView 塞进 ScrollView / 导航容器 | 不适用 | 同上 |
| 6. 全幅背景画不进 pane 里 | **已做（自研等价）** | 播放页分栏左栏 `ZStack { Color.black; watchPlayer }.ignoresSafeArea(edges: .bottom)`，背景画在 pane 外层 |
| 7. `.fill` 图片不能单独当 pane | **已做（自研等价）** | `WatchCoverBackdrop` 去 `aspectRatio` + 依赖 `PosterImage` 内部 `scaledToFill + clipped` |

## 三、iphone-duo-skill · 纵向栏（vertical bars）

| # | 社区建议 | 映匣现状 | 证据 |
|---|---|---|---|
| 3.1 | 只**系统容器**里的 toolbar item 会移到侧边；手搓 `UIToolbar` / 浮动按钮栈**不会**，可能压在摄像头下 | **已做（绕开）**：TabBar 用系统 `TabView`；播放页全屏时**主动隐藏**系统栏并用 `FloatingSectionBar` 自绘——这是「全屏沉浸」的产品选择，且浮动栏可拖拽吸附，不会固定压在摄像头下 | `App/RootView.swift` 的 `tabView`；`映匣功能清单.md` §2.3「浮动分区栏」 |
| 3.2 | 每个 toolbar item 要**同时有 title 和 symbol**（纵向栏只显示 symbol，title 只进溢出菜单） | **已做**：`Label { Text(...) } icon: { Image(systemName:) }` | `App/RootView.swift:tabLabel(_:)`（`Label { Text } icon: { Image }`） |
| 3.3 | 标题栏隐藏 = 手搓 chrome，压 pushed 页面时尤其危险 | **⚠️ 中风险（14 处 `.toolbar(.hidden, for: .navigationBar)`）**：映匣是「自绘大标题」风格，绝大多数页面自绘标题。**pushed 页面**（`Route` build 出来的）如果也隐藏了导航栏，纵向栏里就没有 Back 键——这是真实缺口 | 见下「★ 需要跟进」 |
| 3.4 | 用语义 placement（`.cancellationAction` / `.topBarPinnedTrailing` / `ToolbarItemGroup`），不要手插 Spacer | **未做**：映匣自绘返回键（`Image(systemName: "chevron.left")` 之类），不用 `.cancellationAction` | 同 3.3 |
| 3.5 | `visibilityPriority` 标记必须常驻的动作 | **未做（无适用场景）**：映匣的 tab 是固定的 7 个 section，不用 toolbar item 承载主要动作 |
| 3.6 | 自定义「更多」菜单用 `ToolbarOverflowMenu` | **未做**：`More` 是**一个 tab**（系统 More 或自建 More 页），不是 toolbar 溢出菜单 | `App/MoreView.swift` |
| 3.7 | 语义文本（Select ⇄ Done、购物车合计）加 `.axisBehavior(.horizontalOnly)` | **不适用** |
| 3.8 | badge 数量晚到时，**同时改 symbol**（`bell.fill` → `bell.badge.fill`），否则纵向栏 badge 不刷 | **已做（等价）**：更新角标走 `tabBadge(_:)` 返回 `Text`，配合 iOS 26 系统 TabView 的 badge——**但未做 symbol swap 兜底**。风险：iOS 27 纵向栏下 badge 可能不刷新 | `App/RootView.swift:tabBadge(_:)`。见「★ 需要跟进」 |
| 3.9 | 全屏沉浸页可 `.toolbarVerticalBehavior(.disabled)`，但 Apple 说「一般别」 | **未做（未测）**：映匣全屏播放用 `.toolbar(.hidden)` + 自绘，没走 `toolbarVerticalBehavior(.disabled)` | `App/GlassKit.swift:setBarVisibility(_:for:)` |

## 四、iphone-duo-skill · 折叠区（reserved regions / hinge）

| # | 社区建议 | 映匣现状 | 证据 |
|---|---|---|---|
| 4.1 | 手放的内容要避 `.division`（折叠带 ~40pt，**off-centre**，不是 `width/2`） | **未做**：映匣没有手放内容到折叠线附近的场景——分栏比例是 `detailWidth = width * 0.34`，折叠带正好落在左栏里，**会被播放器画面盖住**，视觉上无害 | `映匣功能清单.md` §2.2「detailWidth = width * 0.34」 |
| 4.2 | 折叠带只在**半折叠**时 `isActive`，完全平展时无效 | **正确假设**：映匣不依赖折叠带，所以半折叠时左右分栏直接跨过折叠带（画面被折），这是可接受的已知行为 | 同上 |
| 4.3 | 摄像头 occlusion 只在用时有效 | **未做（无害）**：映匣浮动分区栏可拖拽，用户可自行避开 |
| 4.4 | `onHingeChange` 只用于**实时特效**，不要用于布局 | **已做（且更严）**：映匣用 `onChange(of: duoExpanded)`（size class 变化）驱动布局，不用 hinge 角度 | `映匣功能清单.md` §2.1「折展时方向锁联动」 |
| 4.5 | 折叠**不是** `scenePhase` 变化 | **已做（且踩过坑）**：映匣明确记录「折展不触发 `onAppear`」，所以把方向锁挂在 `onChange(of: duoExpanded)` 上 | `映匣功能清单.md` §2.1 同上 |

## 六、sunimp/TabBar · 三态 TabBar

它的做法（读源码 `Sources/TabBar/TabBarController.swift:411-499`）：

- 纵向与否、在哪一侧、轨道 frame **全部来自系统**：`UITraitCollection.verticalBarEdge` + `view.layoutGuide(for: .bar(onEdge:extent:))`（轨道宽 48pt）。
- 横向布局时用 `reservedRegions(kind:)` 避开摄像头和折叠区。
- **它是 `UITabBarController` 子类**，三态切换时 **view controller 不重建**，只重排 TabBar 自身。

| # | 对比项 | sunimp/TabBar | 映匣 | 判定 |
|---|---|---|---|---|
| 6.1 | 三态布局来源 | 系统 `verticalBarEdge` + `layoutGuide(for:)` | **系统 `TabView` 自己处理**（`TabView` + `.sidebarAdaptable` / 默认样式），映匣不自己算 | **映匣更省事**：系统组件本来就会移到侧边，不需要 `layoutGuide` |
| 6.2 | 三态切换是否重建内容 | 不重建（VC 复用） | **不重建**：`ForEach(tabs)` 的 id 是 `AppSection.id`，Tab 页 identity 稳定 | 平手 |
| 6.3 | 折叠区避让 | 自己算 | 交给系统 | 映匣更省事 |
| 6.4 | **tab 成员随形态变化** | 不变（固定 items） | **会变**：`barSlots` 4↔7，`tabs` 数组增删条目 | **映匣独有风险**，见 `Duo适配报告.md` §二·P2 |
| 6.5 | 纵向时长按展开显示标题 | 有（自定义交互） | 无（系统行为） | 不适用 |

**结论**：映匣用系统 `TabView` 而非自研 TabBar 是正确取舍——`sunimp/TabBar` 之所以手搓 `layoutGuide`，是因为它绕开了 `UITabBarController` 的系统布局。映匣不绕，就不需要抄这部分。**唯一要抄的是它的「三态下 items 不变」这个隐含约束**：映匣的 items 会变（4↔7），这是 P2 那个 bug 的来源。

## 七、VankerWu/iPhone-Duo-Apps · 适配判定标准

它**不给代码标准**，只给证据分级：

| 它的状态 | 含义 |
|---|---|
| 苹果官方介绍 | Apple 公开资料提到/展示；**不等于实测通过** |
| 用户实测确认 | 有具体版本、使用姿态、可核查证据 |
| 待确认 | 在观察名单，证据不足 |

它的三条硬规矩（README + `DATA_POLICY.md`）值得直接采纳：

1. **「能运行 / 最近更新 / 有 App Store 页」都不算已适配。**
2. **不同版本、地区、内外屏姿态表现可能不同** —— 必须按姿态分列。
3. 自动同步**不得**仅凭名称/上架时间/更新日志关键词把条目改成「已确认适配」。

→ 映匣的对应做法：`Docs/duo/Duo适配报告.md` §四的三态验证矩阵**按姿态分行**，每格独立判读，不给「总体已适配」这种合并结论。这条是本次从它那里吸收的最有价值的东西。
