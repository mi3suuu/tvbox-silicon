## 1. 审查结论（修前）

### BUG-A · blocker · 外屏（合盖竖持）被判成横屏，播放器、胶囊条、底部留白三处同时错

`App/OneSkin.swift` `landscapeNow` 原来写：

```swift
let wideBySizeClass = OneSkinCanvasWidth.isWide(horizontal: horizontalSizeClass, vertical: verticalSizeClass)
let landscapeNow = sizeClassReady ? wideBySizeClass : stageIsLandscape
```

而 `OneSkinCanvasWidth.isWide` 里有一条 `vertical == .compact → 宽屏`（为让「手机横持」成立）。
**Duo 合起外屏竖持实测报 `regular × compact`** —— 竖着的手机被这条规则判成宽屏。

连带三处（全部按横屏公式）：

| 位置 | 横屏公式 | 竖屏应有 |
|---|---|---|
| 窗口高 | `winH = winW / 1.819` | 竖屏分支（顶部留白 + 固定比例） |
| 胶囊条宽 | `columnLeft = 53.34%` | 整宽 |
| 底部留白 | `margin(列宽)` | 28pt |

**实测证据（修前 log）**：`stage box=466x678 shape=column land=false` 之后紧跟
`pictureColumn ... win=466x256`。这里 `win=466x256` 恰是竖屏分支的结果 —— 说明
`shape` 与 `landscapeNow` 在修前已不同步，`shape` 是 column 而布局按横屏算。

### BUG-B · blocker · 内屏竖持被判成「展开横屏」，整页横向溢出 282pt

`App/VideoDetailView.swift`：

```swift
private var landscapeScreen: Bool {  // 读 interfaceOrientation
    switch UIApplication.shared.appWindowScene?.interfaceOrientation { ... }
}
private var sideways: Bool { duoExpanded && landscapeScreen }
```

`layoutSize` 再按 `landscapeScreen` **交换宽高**得到排版基准。
Duo 内屏**竖持**时 `interfaceOrientation` 实测仍报 `.landscapeLeft/.right`，于是：

- `sideways == true` → `oneSkinShape == .split`（左右双列）；
- `layoutSize` 交换 → 基准 **951×669**；
- 而根部 `GeometryReader` 真实容器只有 **669×780**；
- 三栏按 951 分（左列 507 + 间隙 + 右栏 427）铺到 669 上 → **横向溢出 282pt**，
  右栏被推出屏幕。

**实测证据（修前 log，同一时刻两行并存）**：

```
[OneSkin] ROOT proxy=669x780 screen=669x951 use=669x780 fs=false
[OneSkin] stage box=951x669 shape=split/展开横屏·手机横持 land=true frozen=951x669
```

这就是用户报的「展开竖屏后整页往左推移、右边被切掉」。

### BUG-C · high · 竖屏窗口顶边按「画面区高」算，上移 22–30pt，顶栏压进挖孔

`Sources/TVCore/OneSkinWindowGeometryCore.swift` 竖屏分支：

```swift
let top = colH * Metrics.portraitTop   // colH 是「画面区高度」，不是屏高
```

竖屏单列传给 `pictureColumn` 的 `colH` 是 `pictureHeightOf` 的结果
（= 屏高×0.091 + 窗口高 + 屏高×0.04），**不是屏高**。再乘 9.1% 得到的是
「画面区高度的 9.1%」：

| 形态 | 正确（屏高×0.091） | 实际（画面区高×0.091） | 上移 |
|---|---|---|---|
| 外屏 466×678 | 61.7pt | 39.6pt（picH≈435） | **22pt** |
| 内屏 669×951 | 86.5pt | 56.0pt（picH≈615） | **30pt** |

窗口整体上移，顶栏落进灵动岛/挖孔那条带 —— 用户报的「竖屏时控件没有避让摄像头」。
注意：`OneSkinSafeArea` 的传感器避让本身是对的（按水平位置分别判），
但它只在**窗口坐标系**里下压顶栏；窗口自己先上移了，避让再准也救不回来。

### BUG-D · high · 「转个方向就浮出应用外小窗」——面积差判据对 Duo 最有代表性的一对动作恒为 0

`App/RootView.swift` 版式变化判据原来是**面积差**：

```swift
let before = lastSize.width * lastSize.height
let after  = size.width * size.height
return abs(after - before) / max(before, after) > 0.08
```

Duo 内屏竖持 669×951 与横持 951×669 **面积完全相同**（都是 636,219 pt²），
面积差恒等于 0 → `layoutChangedAt` 不更新 → `PlaybackExit.decide` 里
`layoutJustChanged == false` → 只要那一刻在后台（合盖正好收起手机）就被判成
「离开 App」而起 PiP。

### BUG-E · high · 锁定后陀螺仪一直在采样；锁定态在形态切换重建后丢失且**无法解锁**

两处独立缺陷：

1. `PlayerOrientation.lock()` 调了 `UIDevice.beginGeneratingDeviceOrientationNotifications()`，
   全仓**没有任何一处** `endGenerating…` —— 锁一次后整个进程永久采样，直到 App 被杀。
   用户的要求正好相反：「锁屏防误触模式下屏蔽握持态陀螺仪感应」。

2. `OneSkinChrome.locked` 是 `@State`，而控件层在**每次形态切换**时重建
   （窗口尺寸变，`winW×winH` 变）。重建后 `locked` 回到 `false`，可
   `PlayerOrientation.isLocked` 仍是 `true`：
   - 界面看是「未锁定」——顶栏/播放键/进度条全部回来且可点；
   - 方向其实还钉死着，按键响应了画面不动；
   - 而且不再画 `unlockButton`，用户**没有任何入口解锁**，只能退出页面再进。

### BUG-F · medium · 顶栏「字幕」键点了没反应 / 绕过菜单盲选第一条

`App/OneSkinPlayerChrome.swift` `controlButton(.subtitles)`：

```swift
iconButton("captions.bubble", ...) { chosenSubtitle = subtitleTracks.first?.id }
```

- 只有内嵌字幕轨（`kit.tracks.legible`）、没有外挂 `.srt` 时 `subtitleTracks` 为空
  → 点一下**什么都不发生**；
- 有外挂字幕时直接跳第一条，用户既看不到列表也关不掉。

与画质/音轨那两颗（都弹 `Menu`）不一致，正是「有的控件有效、有的无效」。

## 2. 修法

| BUG | 文件 | 改法 |
|---|---|---|
| A | `App/OneSkin.swift` | `landscapeNow = effectiveShape.isLandscape` —— 横竖**只认调用方给的离散形态**，不再用 size class 二次推断 |
| B | `App/VideoDetailView.swift` + `Sources/TVCore/OneSkinStageSize.swift` | 新增 `OneSkinShapeResolver.isLandscape`：方向信号与**窗口实际比例**冲突时以窗口为准，带滞回；只对大屏（短边 > 600）生效，外屏/普通手机原样不动。读 `window.bounds`（UIKit 所有），**不**读 `proxy.size`（避免自反馈环） |
| C | `Sources/TVCore/OneSkinWindowGeometryCore.swift` + `App/OneSkin.swift` | 几何新增 `portraitTopInset` 参数；竖屏分支由调用方传入 `箱高×0.091`（= 屏高×0.091）。`pictureColumn` 与 `pictureControls` **共用同一个值**（历史上「两处各算一份」必错位） |
| D | `Sources/TVCore/OneSkinStageSize.swift` + `App/RootView.swift` | 新增 `OneSkinStageSize.isLayoutChange`：**逐轴**相对变化 > 8%；替换面积差 |
| E | `App/PlayerView.swift` / `App/OneSkinPlayerChrome.swift` | `lock()` 在 pin 完成后立即 `endGenerating…`；控件层 `onAppear` 从 `PlayerOrientation.isLocked` **回读**锁定态 |
| F | `App/OneSkinPlayerChrome.swift` | 字幕键改为弹 `Menu { subtitlePicker }`，与画质/音轨同构 |

### 为什么不把 BUG-B 修成「每帧读 `proxy.size`」

`layoutSize` 的注释里记着一次事故：测量自身 → 回写布局基准 → 再测量，右侧浅色列
不断往左推进。所以本轮用的是 `window.bounds`（归 UIKit 所有，只随系统旋转/折叠变化），
且加了滞回（进 1.15 / 退 1.05），动画扫过临界点时不翻转。

# 追加：外屏横竖 + 全屏横竖（2026-11-11 补）

用户追加要求：**「外屏要能横屏也能竖屏，全屏也要能横屏也能竖屏」**。
按这条复查，又查出 4 处直接阻断它的代码。

## BUG-G · blocker · 外屏被 `holdPortrait` 钉死竖屏

`App/VideoDetailView.swift` 两处：

```swift
// onAppear
if oneSkinActive { PlayerOrientation.holdPortrait(false) }
else { PlayerOrientation.holdPortrait(!duoExpanded) }   // ← 外屏（未展开）= holdPortrait(true)
// onChange(of: duoExpanded)
PlayerOrientation.holdPortrait(oneSkinActive ? false : !expanded)  // ← 同上
```

`holdPortrait(true)` 把 `mask` 锁成 `.portrait`。外屏（`duoExpanded == false`）落进这一支，
于是外屏**横持会被系统强行拉回竖屏**，旋转键也无效（`rotate(to:)` 只改 mask，
而页面每次 `onAppear`/折叠都再把它锁回竖）。
原版 / 哔哩哔哩皮肤下这个问题一直存在；One 皮肤因为有一支 `false` 才幸免。

**修法**：两支统一改为 `holdPortrait(false)` —— 页面不再钉任何方向。

## BUG-H · high · `PlayerOrientation.suspend()/restore()` 替用户决定方向

```swift
static func suspend() { if mask == .landscape { set(landscape: false) } }   // 展开时把横屏锁降回竖屏
static func restore() { if !isLocked { set(landscape: !holdsPortrait) } }   // 折回外屏强推一个方向
```

`PlayerView` 在 `horizontalSizeClass == .regular && verticalSizeClass == .regular`
（= Duo 展开）时调 `suspend()`。用户刚设好横屏，一展开就被降回竖屏 —— 与「展开横持」直接冲突。
这两个函数建立在「外屏默认横屏、内屏忽略方向」的旧假设上，已被用户要求推翻。

**修法**：都改成空实现，并在注释里写明「这里曾经有个方向策略，现在它被取消了」——
保留调用点是为了让语义有痕迹，不是遗漏。

## BUG-I · high · 全屏竖的那一侧请求的是 `.allButUpsideDown`，等于「你随便挑」

`App/PlayerView.swift` `set(landscape:fullScreen:)`：

```swift
if fullScreenOwnsOrientation { mask = landscape ? .landscape : .allButUpsideDown }
//                                                    ↑ 竖的一侧放开了
geometry = landscape ? .landscape : .allButUpsideDown  // ← 落点交给系统按物理握持挑
```

`requestGeometryUpdate(.allButUpsideDown)` 只表达「除倒置外都允许」，**落点由系统按握持决定**。
用户横着拿手机点「旋转到竖屏」，系统照样挑 landscape —— 表现就是「全屏只能横，转不回竖」。

**修法**：全屏态两侧对称钉住 `landscape ? .landscape : .portrait`。

## BUG-J · blocker · 全屏用的是冻结盒，转屏不跟随

```swift
if fullScreenNow {
    pictureColumn(box, landscape: landscapeNow, fullScreen: true, ...)   // ← box = frozenBox
}
```

`frozenBox` 只在 `onAppear` / `shape` 变化时重算，**不跟旋转走**。
而全屏恰好是用户唯一会「在同一形态里反复转屏」的界面：外屏进全屏后转横，
`shape` 仍是 `.column`（外屏合盖不分横竖双列）→ 盒不重算 → 竖盒铺在横屏上，两侧各露黑边。

**修法**：全屏改用 `stage(_ size:)` 收到的 `size`（= 根部 `GeometryReader` 的 `avail`）。
这是安全的：它**不参与任何 layout 回写**（不同于 `StableStageSize` 写 `@State` 驱动重排），
只是本次绘制的输入，不会形成 `layoutSize` 注释里记的自反馈环。

# 轮次三：细读代码后新发现并修复的 5 个缺陷（BUG-K ~ O）

前一轮是对齐 6 份 GitHub skill；这一轮是**逐行细读播放器链路**，又找出 5 个此前没暴露的问题。
每个都先修、再推演、再补回归测试。

## BUG-K · 胶囊条错位 145pt（确定性算术）

画面列高度在 `fullBleed` / `halfFold` 分支里按**片源比例**算，
而控制栏胶囊条的底距在 `stage` 外层 `.oneSkinOverlayOnce` 里**另算一份**，
且那份写死的还是改造前的固定比例 `box.height * 0.56`。

| 片源 | picH（真实） | 修前底距 | 修后底距 | 误差 |
|---|---|---|---|---|
| 16:9 | 376.3 | 477.8 | 622.8 | **−145.0** |
| 4:3 | 501.8 | 477.8 | 506.4 | −28.6 |
| 9:16 | 532.6 | 477.8 | 477.8 | 0 |
| 2.35:1 | 284.7 | 477.8 | 707.8 | **−230.0** |

竖片恰好撞上限，所以「看不出问题」—— 这正是它长期漏检的原因。

**修法**：抽出 `bleedingPictureHeight(_:aspect:lower:upper:)`，
画面分支与胶囊条**共用同一个函数**；三处调用点全部改走它。

## BUG-L · 三形态控制栏在内屏竖持永远读错配置

`PlayerControls.currentShape` 用 `interfaceOrientation` 分横竖，
而内屏不遵守 supported orientations（`device-facts`），实测恒报 landscape
→ 竖持被算成 `.sideways` → 用户为「展开竖持」排的那套配置**一次都读不到**。

**修法**：新增 `current(forSkinShape:width:)`，直接由 `OneSkinShape` 映射配置档位：

| 形态 | skinShape | 档位 |
|---|---|---|
| 外屏合盖 | `.column` + 窄 | `.folded` |
| 内屏竖持 | `.fullBleed` | `.unfolded` |
| 内屏横持 | `.split` | `.sideways` |
| 半折 | `.halfFold` | `.unfolded` |

⛔ **不能按窗口宽高比判**：播放器窗口恒为横向（1.819），
竖持 fullBleed 窗口是 669×532、单列是 669×345，两者都「宽>高」，
按比例判会全部算成 sideways。这条已写成测试 `thePlayerWindowIsAlwaysWiderThanTall` 钉住。

## BUG-M · 旋转键在内屏失效

`onRotate` 用 `interfaceOrientation` 取反。内屏竖持报 landscape →
`set(landscape:false)` → 请求竖屏，而用户本来就是竖的 → **点了没反应**。
外屏是普通 iPhone 语义所以正常，这个 bug 只在展开后出现。

**修法**：`nowLandscape = (oneSkinShape == .split)` —— 与版面、控制栏同一个形态真源。

| 场景 | 修前 | 修后 |
|---|---|---|
| 外屏竖持 | 转横 ✓ | 转横 ✓ |
| 外屏横持 | 转竖 ✓ | 转竖 ✓ |
| 内屏竖持 | **原地不动** ✗ | 转横 ✓ |
| 内屏横持 | 转竖 ✓ | 转竖 ✓ |

## BUG-N · One 皮肤从不更新片源比例

`syncAspectFromPresentationSize()` 只挂在**哔哩哔哩分支**（`VideoDetailView.swift:1593`），
One 分支没有；`OneSkin.swift` 里那段 `presentationSize` 轮询也早被删了。
于是 One 皮肤的 `aspectRatio` 永远是 16:9 初值：

- 竖屏片源在 fullBleed 下 `picH = 669/1.778 = 376.3`，**应为 532.6**
- 画面被压成中间一条、上下大黑边

直接违反项目铁律「画面比例唯一真源是 `presentationSize`」。

**修法**：One 分支挂上**同一个** `.task(id: playerSession?.player.currentItem)`，
两个皮肤不再各有一套比例来源。

## BUG-O · 遮挡避让算两遍 + 灵动岛模型是直板机的

两层叠加：

| 层 | 位置 | 作用 |
|---|---|---|
| A | `VideoDetailView.safeAreaPadding(.top, occlusionInsets.top)` | 把**整棵页面**推下去，`box` 变小 |
| B | `OneSkinChrome` 里 `housing` + `clearedCentreY` | 在窗口坐标系内再压一次顶栏 |

`occlusionInsets.top` 是遮挡矩形的**绝对下边界**（`rect.maxY`，从容器顶算起），
而系统**已经**把内容推到了 `safeAreaInsets.top` —— 同一坐标系里语义重叠，直接相加 = 推两遍：

| safe.top | occlusion.top | 直接相加 | 该补 |
|---|---|---|---|
| 84 | 60 | 144 | **0** |
| 84 | 100 | 184 | **16** |
| 0 | 84 | 84 | **84** |

另外 `housing` 的「屏宽 × 0.27 + 水平居中」是**直板 iPhone** 的灵动岛形状，
而 `device-facts` 写明 Duo 的岛是**竖排贴边**的 → 横向范围整个算错，
结果是「中间顶栏被无谓下压、真正压住控件的侧边没让开」。

**修法**：
1. 新增 `OneSkinSafeArea.topUp(occlusion:safe:)` = `max(0, occlusion - safe)`，
   由 `occlusionTopUp(_:fullScreen:)` modifier 应用；
2. `housing` 在 Duo 宽度（短边 ≥ 460）下取**整宽避让** —— 宁可整体下移，绝不漏让。

# 轮次四：继续细读后修的 2 个缺陷（BUG-Q / BUG-S）+ 1 处死代码

## BUG-Q · 折叠探针的「重读触发」形同虚设

`FoldRegionProbe` 被 `.frame(width: 0, height: 0)` 压成零尺寸，
所以 `proxy.size` **恒为 `.zero`，永远不变** ——
`.onChange(of: proxy.size) { read(proxy) }` 一次都不会触发。
整个折叠检测只剩 `onAppear` 那一次：

- 进页面时是摊开的 → `foldGap` 一直 `nil`，后来折到半折也不更新；
- 进页面时是半折的 → `foldGap` 一直有值，摊开后也不会清掉。

表现就是「半折形态识别不到 / 摊开了还按半折排版」。

**修法（三层触发，缺一不可）**：

| 触发源 | 覆盖的转换 |
|---|---|
| `onAppear` | 首次进入 |
| `onChange(of: verticalSizeClass)` | 折叠/展开（size class 翻转） |
| `onChange(of: screenSize)` | 换屏、Split View、PiP 压短 |
| `onChange(of: scenePhase)` | 前后台切换兜底 |
| **`onHingeChange`**（27.1+） | **摊开 ⇄ 半折** —— 尺寸与 size class 都不变，只有折痕出现/消失，**只有这一路抓得住** |

铰链信号只用来**触发重读**，不拿角度算布局（`duo-media` / `adaptive-layout` 都强调这一点）。
用 `.id(foldReadTick)` 强制重建探针；`apply()` 里逐项比对后才写 `@State`，值没变就不写 → 无自激。

## BUG-S · 形态不变但可用空间变了 → 冻结盒不重算

`frozenBox` 原来只在 `onAppear` 与 `onChange(of: shape)` 时重算。
但**形态可以不变、空间却变了**：

- Duo 内屏进 Split View → 宽度 951 → 约 475，`size class` 仍 regular×regular、
  `duoExpanded` 仍 true、`oneSkinShape` 仍是 `.split` —— `shape` 一个字都没变；
- PiP 钉在顶部把窗口压短，同理。

于是 box 停在 951×669，真实可用只有约 475 宽 —— 三栏按 951 分、铺到 475 上，右侧被推出屏幕。

**修法**：新增 `.onChange(of: OneSkin.fixedScreenSize())`，
用**屏幕实际尺寸**（静态值，不受旋转动画影响）当触发源，
并用 `OneSkinStageSize.isLayoutChange`（逐轴 >8%）过滤亚点抖动。

| 场景 | 触发 |
|---|---|
| 内屏全宽 → Split View 半边 | ✓ 475/951 差 50% |
| 内屏 → PiP 压短 | ✓ 480/669 差 28% |
| 旋转动画亚点抖动 | ✗ 0.05% |
| 真的折叠 669 → 951 | ✓ |

## 死代码 · `OneSkin.screenIsLandscape()`

全仓零调用，且实现与 Duo 事实相反（按 `interfaceOrientation` 判横竖，
而内屏不遵守 supported orientations，实测恒报 landscape）。
留着只会误导后来的人以为「这里有可信的方向判断」。**已删**，并留注释说明为什么删。

## 顺手修的一处「单一真源没被使用」

`OcclusionTopUp` modifier 一开始自己重写了一遍 `max(0, a - b)`，
而 `OneSkinSafeArea.topUp` 才是那条公式的真源 —— 于是同一套算术存在两份，
其中一份没有单测覆盖。已改为调用真源（并在 `FoldRegion.swift` 引入 `TVCore`）。

# 轮次五：补齐第五点需求 + 测速缺口 + 界面功能盘点

## 一、第五点「锁屏防误触屏蔽握持陀螺仪」真正落地

### 先划清能力边界

查证了 6 个 skill 仓库与 Apple `Prepare for iPhone Duo`，结论：

| 层面 | 能否阻止握持转向 | 依据 |
|---|---|---|
| **外屏** | ✅ 能 | `duo-games` 实测：只支持横屏的构建，合盖竖持时确实跑成 678×466 横屏 |
| **内屏** | ❌ **不能** | 同一实测：桌面半折时「**lock or not**」都拿到 669×951 竖高窗口 |

`iphone-duo-skills/device-facts`："The inner display does not honor your supported interface orientations — it rotates regardless."
Apple `prepare` 只说「orientation 不能用来做布局决策」，从未承诺方向掩码在 Duo 上有效。

**所以内屏上唯一能兑现的防误触是：锁定后自己不再理会握持变化。**

### 实现：锁定态冻结横竖（`VideoDetailView.sideways`）

```swift
private var sideways: Bool {
    if let frozen = landscapeFrozenWhileLocked, frozen.expanded == duoExpanded {
        return duoExpanded && frozen.landscape
    }
    return duoExpanded && landscapeScreen
}
```

关键判据 —— **只冻结横竖，绝不冻结 `duoExpanded`**：

| 事件 | 本质 | 锁定后 |
|---|---|---|
| 握持转向 | 同一形态、同一窗口，宽高互换 | **忽略**（用冻结值） |
| 折叠 / 展开 | 形态本身变了（`duoExpanded` 翻转） | **永远响应** |

把折叠一起冻住会让画面留在内屏布局、外屏一片空白 —— 所以 `LandscapeFreeze` 带一个 `expanded` 字段，形态一变旧冻结值自动失效。

配套：
- `PlayerOrientation.lock()/unlock()` 广播 `lockStateDidChange`
- `VideoDetailView` 用 `.onReceive` 回读（锁钮在 `OneSkinPlayerChrome` 里，隔多层视图，广播比穿透闭包干净）
- `onAppear` 也回读一次，否则「锁着进来」时冻结值是 `nil`

## 二、测速按钮：确认有缺口，已补

### 查证结果

已实现的部分比预期多：`SourceProbeRunner`（延迟+稳态吞吐+分辨率）、`SourceProbeStore`（按 `sourceKey|videoID|lineFlag` **三维**缓存）、`SourceSpeedTestView`（全量 sweep/筛选/直连代理切换/拖拽排序）、`EpisodePicker`（按线路逐条测，且会先 `resolve` 成真实地址）。

**真缺口三个，已修两个：**

### 缺口 1 → 已修：「换个源看」从不测速

`CrossSourceSheet` 只读 `SourceProbeStore.latest(sourceKey:)` 的旧缓存。

### 缺口 2 → 已修：没有「同剧跨渠道 × 跨线路」的聚合测试

# 轮次六：探针采集四项 + 按优先顺序探测 + 测后自动重排 + 全量并发提速

## 一、探针采集能力补齐（分辨率 / 码率 / 色域 / 文件大小）

### 修前状态

`SourceProbeResult` 只有 `resolutionHeight`，而 `ResourceRanking.Key.Attribute` 有四项目：
`resolution` / `bitrate` / `fileSize` / `colourRange`。
`Attribute.speedTestProvides` 写死 `self == .resolution` ——
于是设置页里按码率、文件大小、色彩范围排序**三项全是空开关**，`SourceSpeedTestView` 的
footer 自己写着 "measures resolution only"。

### 修法

新增 `SourceProbeRunner.declaration(in:url:)`，**一次**从 m3u8 主列表头里解析三个量：

| 量 | 来源标签 | 备注 |
|---|---|---|
| 分辨率 | `RESOLUTION=1920x1080`，退回文件名 `1080p` | 原有逻辑保留 |
| 码率 | `BANDWIDTH=`（峰值），退回 `AVERAGE-BANDWIDTH=` | m3u8 是 bit/s，除 1000 存 kbps |
| 色域 | `VIDEO-RANGE=SDR\|HLG\|PQ` | 非标准值丢弃，不猜 |

文件大小走响应头，不进 m3u8：新增 `totalBytes(from:)`。

**⛔ 关键判据：只认 `Content-Range` 的总分母。**
分片响应的 `Content-Length` 报的是**这一片**（我们只要 256 KB 它就报 256 KB），
拿它当文件大小会把每个源都记成 256 KB。只有状态码 200（服务端忽略了 Range、全量返回）
时 `Content-Length` 才等于文件长度。

头也从 4 KB 提到 8 KB —— 四标签共存时 4 KB 可能截断。

### 四项全部参与排序（`sortScore` 从四段扩到七段）

| 段 | 权重 | 理由 |
|---|---|---|
| 可达性 | 0–100 | 门槛 |
| 速度 | 0–30 | 4 Mbps 饱和（多出来的带宽不产生画面） |
| 延迟 | 0–15 | ≤300 ms 满分 |
| 分辨率 | 0–20 | 用「有效画质」压掉虚标 |
| **码率余量** | **0–10** | **实测吞吐 ÷ 声明码率**：≥2× 满 10，1× 得 5（卡顿边缘），<1× 递减 |
| **色域** | **0–5** | 只奖励 HDR；不惩罚 SDR（SDR 在 SDR 屏上是正确的，不是缺陷） |
| **文件大小** | **0–5** | 小文件轻加分；>8 GB 不加也不减（大片天然大） |

码率余量是最有价值的一段：它直接回答「这条线喂不喂得饱这路流」，
比任何绝对数字都贴近「会不会卡」。

## 二、按点播源优先级顺序执行探测

`probeTargets` 一直走 `sourceGroups(...)` 的顺序 —— 那就是用户在「整理源」里排好的优先顺序。
本次把这个性质**显式记录**在注释里（此前没写明，容易被当成任意顺序），
不做改动，因为它本来就是对的。

## 三、测速后自动调整优先顺序

### 修前状态

`SourceProbeResult.sortScore` 算得很细，但**没有任何一处把它写成顺序** ——
得分只用来上色与单次择优，源的优先顺序永远停在用户手排或导入时的原样。
「测完速」对搜索与列表顺序毫无影响。

### 修法

`SourceOrder.reorderByProbe(...)` + 抽出的**纯核心** `probeOrder(_:existing:score:pinnedKeys:)`，
在 `runProbe` 结束时调用 `Store.reorderSourcesByProbeResult()`。

三条优先级，顺序不可换：

1. **钉住的永远最前**，且彼此保持原有次序 —— 用户显式钉过的意图高于任何测量；
2. **测过的按分数降序**，同分保持原有次序（否则每次测速顺序都乱跳，像在抽风）；
3. **没测过的按原次序垫后** —— 没测过 ≠ 坏，但也不该压过测过的。

为什么把核心抽成纯函数：`Site` 是 Codable 解码构造，测试里造实例很别扭；
`probeOrder` 只吃 `[String]` 与闭包，7 项单测能直接把规则钉死。

## 四、全量并发提速（解决「探测缓慢」）

### 根因

`ProbeSchedule.standard.measureWidth = 4`，这个值当初是按
「阶段 2 要跑插件、编译会抢 CPU」定的。但**线路测速是纯 HTTP**（一次 Range 请求），
瓶颈在网络与主机轮换，不在 CPU。设成 4 意味着 340 个源要排 85 轮、每轮约 3 秒 →
**4 分钟以上**，「探测缓慢」就是这个。

### 修法

新增 `ProbeSchedule.bulk`：`screenWidth 24 / measureWidth 16`。

| 调度 | 阶段1 | 阶段2 | 340 源预估 |
|---|---|---|---|
| standard（增量） | 16 | 4 | ~4.3 分钟 |
| **bulk（全量）** | **24** | **16** | **~1 分钟** |

`startProbingAllSources(fast: true)` 默认走 bulk；增量扫描仍用 standard。

**上限不设更高（如 64）的理由**：源站多为中小站点，单站被并发打 16 次已接近容忍边界，
再高会把好源打出 5xx，反而制造假「不可达」—— 提速不能以准确度为代价。

## 🔴 最严重：LineMatrix 行排序方向反了 + 比较器违反严格弱序

子代理用**实跑**（把真实源文件独立编译执行）证明：

| | 修复前 | 修复后 |
|---|---|---|
| `build([Zeta:4000kbps, Alpha:900kbps])` | `Alpha(900)` 排第一 | `Zeta(4000)` 排第一 |

根因两处，都在同一行：
1. **方向反了**：`better(rb, lb) → return true`，而 `better(rb,lb)` 为真表示 **rhs 更好**，却让 lhs 排前面。
2. **不构成严格弱序**：`better(rb,lb)` 为 false 时**没有 `return false`**，直落到名字兜底，实际语义变成 `cmp(A,B) = better(B,A) ? true : (A.name < B.name)`。于是「A 更好且 A 名字更靠前」时**双向都返回 true**。

第 2 条的后果更隐蔽：子代理实测「同一份 6 源输入连跑 4 次进程得到 4 种不同顺序」——
恰好与那行注释写的「名字稳定排序，避免每次刷新顺序乱跳」完全相反。

修法：方向修正 + 两个方向都判 + 全并列时用 `sourceKey` 兜底（保证全序）。

## 🔴 `warmupBytes` 局部变量遮蔽静态常量 → 稳态测速从未生效

`stream()` 里 `var warmupBytes = 0` 与静态常量 `warmupBytes = 96*1024` **同名**，

子代理实测（4 KB/tick、256 KB 预算）：预热边界落在 4096 而不是 98304，
**真正排除的慢启动只有 1.56%** —— 注释里宣称的「排除 43% 慢启动、与 RTT 无关的稳态速度」一行未实现。

## 🔴 `declaredConflicted` 非 Optional → 老用户测速读数永久丢失

我新增的 `declaredConflicted: Bool = false` 是**非 Optional 存储属性**。
Swift 合成的 `init(from:)` 要求非 Optional 键必须存在（**属性默认值不参与解码**），

`FullBackup` 白名单也含这两个键，备份恢复同样读不出来。

# 轮次七（续）：5 个子代理共抓到 11 个真 bug，全部已修

## 🔴 `shape(for:width:)` 的 560 闸门让 `sideways` 整段不可达

上一版写成「先 `width < 560 → .folded`，再 `case .split → .sideways`」，
而**两个调用点传的 `width` 都是播放器窗口宽 winW = 左列宽 ≈ 屏宽 × 0.5334**：

| 场景 | winW | 旧结果 | 应为 |
|---|---|---|---|
| 内屏横持 split | 951 × 0.5334 = **507.3** | `.folded` | `.sideways` |
| 手机横持 split | 678 × 0.5334 = **361.6** | `.folded` | `.sideways` |
| iPad 横持 | 1024 × 0.5334 = **546.2** | `.folded` | `.sideways` |

「凡 split 形态，winW 恒 < 560」→ `case .split` 是**不可达代码**，
用户单独配的 `playerControlsOrder.sideways` **一次都读不到** ——
这是「设置里改了没反应」换了个成因复发。

**修法**：`split` 先于任何宽度闸门返回。**形态本身已是可靠信号**（调用方用

宽度只用于区分「宽屏竖持」与「窄屏竖持」。

## 🔴 半折没接入 `bleedingPictureHeight` → 胶囊条偏 122pt

上一版只特判 `.fullBleed`，半折掉进 `pictureHeightOf` 分支（另一套比例）。

→ **偏 122.1pt，扎进半折控制台**（那是半折形态唯一的交互面）。横持 120pt、678×466 85pt。

**修法**：半折走同一条通道，用它的 0.30/0.55（与 `pictureColumn` 一致）。

## 🔴 `release()` 静默清锁不发广播 → 版面永久冻结

`PlaybackView.onDisappear` **无条件**调 `release()`，而折叠/展开会拆掉 PlaybackView。
于是「锁定 → 合盖」把锁静默清掉，但版面层 `lockedForShape` 仍 true、冻结值仍在
→ **控件显示未锁定、方向真的未锁、但版面永久冻结**，只能退页重建。

更糟的是组合死锁：`release()` 已把 `isLocked` 置 false ⇒ 用户点锁钮走的是 `lock()`；
即便走到 `unlock()` 也有 `guard isLocked else { return }` 早退、广播照旧不发。

**修法**：`release()` 记下 `wasLocked`，真的变了才广播。

## 🔴 锁定瞬间可能读到转向动画中间帧 → 冻结值写反

原做法是让版面层在 `onChange` 里现读 `landscapeScreen`，但那读 `window.bounds`（连续量）。

## 🔴 测死的源仍在显示旧数字（只报喜不报忧）

# 轮次八：子代理遗留的 6 项全部修完

轮次七记录了「明确未改」的几项，本轮全部补上。

## 🔴 横屏刘海避让曾是死代码 —— 用户最早报的「最边缘点不到」终于修了

`housing()` 第一行是 `guard safeTop > 0 else { return .none }`。
而横屏时 `safeAreaInsets.top` **通常是 0**（刘海在**左缘**，是竖向缺口）→ 直接返回 `.none`
→ `Housing.bottom = 0` → `overlaps` 里的 `guard bottom > 0` 恒 false
→ 那句 `let notch = max(safeLeft, 44)` **永远执行不到**。

函数自己的文档注释（本文件开头 20–22 行）就写着这个场景，实现却没兑现。

**修法**：
- 判据分开：**竖屏看 `safeTop`，横屏看 `safeLeft`**，任一为 0 才算没遮挡
- 横屏的 `bottom` 取 `max(safeTop, 56)` —— 刘海是贯穿左上角的竖向缺口，
  纵向至少覆盖顶栏那一排；不这么写 `overlaps` 又会因 `bottom == 0` 再次把判据废掉

新增 `OneSkinSafeAreaHousingTests`（4 项）：横屏 `safeTop=0` 时最左按钮必须判定撞上、
中部按钮不被连累、Duo 竖排岛取整宽避让、无遮挡时返回 `.none`。

## 🔴 并发峰值不是 16 而是 64 —— 接上 host 级限流

`measureWidth = 16` 是**源级**并发，而每源内部还会对多条线路并发（上限 4）
→ 实际峰值 16 × 4 = **64**。轮次七那句「单站被打 16 次已近容忍边界」的论证按 64 不成立。

真正的闸门是 `LineRotation.maxConcurrent`（默认 4，按 **host** 计的在飞计数 + 退避），
而它原先**只有 `EpisodePicker` 一处在用，扫描路径完全绕过**。

**修法**：
1. `Store.probe(_:)` 的每线路任务里接入 `beginBase` / `succeedBase` / `failBase` ——
   被判 saturated 或冷却中的 host 跳过这条线路（**不是判它死**，与 `EpisodePicker` 同语义）
2. 有了 host 闸门，源级才敢开大：`bulk.measureWidth` 16 → **32**（340 源约 11 轮，
   而单站峰值恒 ≤4）

## 🔴 测速无总时限无取消 → 最坏 30–45 分钟不返回

每个候选源内部有单次 probe 的 8 秒超时，但**源数 × 线路数**累起来没有上界。
`Store` 早就有 `withDeadline` 却没用在这里。

**修法**：
- `crossSourceProbeBudget = 20 分钟`（依据：最多约 60 候选、并发 4、每源最长 8 秒，
  正常约 75 秒；20 分钟是「极慢但还没死」的上界）
- 到时限停止续投新任务，**已完成的读数照常保留**
- 新增 `cancelCrossSourceProbe()` + `probeTask` 句柄，用户可真的停止；
  `for await` 里检查 `Task.isCancelled` → `group.cancelAll()`

## 🔴 两颗按钮不互斥 + 「重新搜索」抹掉测速状态

- 两颗按钮各自只看自己的标志 → 「测试连通性」跑着时还能点「全部线路」
  → 4 + 3 = 7 路并发同时打几十个源。**已改为互相检查**。
- `searchCrossSource` **整体替换** `crossSource` → 把 `probing`/`matrixRunning`/`readings`/
  `matrixCells`/`probed` 一并抹掉；而「重新搜索」的 disabled 只判 `state.running`，
  测速期间它是 false 故可点 → 标志被绕过、第二轮叠在第一轮上（`probed` 会超过 `probeTotal`）。
  **已改为保留测速字段、只重置搜索字段**。

## 🟡 矩阵区溢出 sheet

20–60 源 × 若干线路全部铺开会把 sheet 顶爆：候选列表与页脚被挤出可视区，

# 轮次九：半折（halfFold）形态补齐 + 模拟器验证边界纠正

## 先纠正我自己的一个错误判断

上一轮我说「Xcode 模拟器可以半折验证」。**实测证否。**

`Scripts/hinge/scripts/hinge` 的 `half` 命令设的是**铰链角度**（0–180°），
它切换的是「用哪一块物理屏」，**不产生「上下两半」的 division 矩形**。

角度扫掠实测（`Docs/duo/evidence-2026-11-11/hinge-angle-sweep.txt`）：

| 铰链角度 | active display | 说明 |
|---|---|---|
| 0° | LCD（1398×2034，外屏） | 合盖 |
| 90° | LCD-1（2007×2853，内屏） | 半开，**仍只有一块屏亮** |
| 135° | LCD-1 | |
| 180° | LCD-1 | 摊平 |

**全程只有一块 active display**，从来没有「两块屏上下并排」的几何。
而 `.halfFold` 的判据是 `FoldGap.horizontalBand` —— 要求
`reservedRegions(kind: .division)` 给出一个 `width > height` 的**横向**矩形。
横折痕不存在 → 该判据恒 nil → `.halfFold` 在模拟器上**不可达**。

结论：半折只能在**真机**（把 Duo 摆成帐篷/书本姿态）验证。
模拟器能验的是「加了 halfFold 之后前四态没被破坏」，不是半折本身。

# 轮次十：按 One 1.7.1 原版结构重写几何（根治「推移」）

## 方法：先拉原版真结构，再动手

用 `rea/MachOSwiftSection/bin/swift-section interface` 解析
`One_1.7.1_致敬韩寒.ipa` → `Payload/One.app/One`，得到 **284 个 Swift 类型**。
（证据：`Docs/duo/evidence-2026-11-11/One-1.7.1.interface.swift`）

## 决定性发现：原版**没有**逐帧几何依赖

```swift
struct VideoDetailPage {
    var _wide: One.LargeCanvas                    // ← 宽屏判据
    var __pageSize: SwiftUI.State<CGSize>         // ← 页面尺寸，一次写入
    var __division: SwiftUI.State<CGRect?>        // ← 折痕
    var __bodyExpanded: State<Bool>
    // …
}

struct LargeCanvas {
    var _horizontal: Environment<UserInterfaceSizeClass?>
    var _vertical:   Environment<UserInterfaceSizeClass?>
}
```

`LargeCanvas` **没有任何像素字段** —— One 判宽屏只看 **size class**。

| | One 1.7.1 | 我们（改前） |
|---|---|---|
| 宽屏判据 | size class（离散） | GeometryReader 量宽高比（连续） |
| 页面尺寸 | `__pageSize: State`（一次写入） | `frozenBox` + 每帧 `proxy.size` |
| GeometryReader | **0** | **14** |
| 结果 | 稳定 | **自反馈环** |

## 环的铁证（Fig 日志，dt=28–40ms 每帧）

```
proxy.width: 1210→1196→1178→…→725   （36 帧连续 -14）
             725 → 803 → 1268        （突然重置）
             1268→1248→1236→…        （再收缩）
proxy.height: 恒 294（screen 669，差 375）
```

`669 - 294 = 375pt`，**无法用任何系统安全区解释**
（Home 34 / TabBar 49 / 导航 44 / 状态 59）。
⇒ 294 是 `GeometryReader` 在高度未定的父级里，**用子视图理想高度反推**得到的。

而 `stage()` 的 5 个 `if/else` 分支返回高度不同、且最外层没有 `.frame` ——
内容高度不受限，父级就按内容上报。

## 改动（两处，都是「把连续量换成容器」）

### ① `box` 改为容器优先

```swift
// 改前：box 只来自 frozenBox（屏幕 669×951）→ 内容 951 高
// 改后：
let box: CGSize = (size.width > 1 && size.height > 1) ? size : screenBox
```

`frozenBox` 降级为「首帧兜底」，不再参与像素计算。

### ② `stage` 返回值显式声明「我占容器大小」

```swift
.frame(width: max(1, box.width), height: max(1, box.height), alignment: .topLeading)
```

放在修饰符链**最外层**（`.padding` 之后）。上报值与容器一致 → 父级无需重协商 → 环断开。

## 三形态静态推演（改后）

| 形态 | box | split 左/右列 | fullBleed 画面高 | 内容总高 |
|---|---|---|---|---|
| 外屏竖持 466×678 | 466×678 | 249 / 218 | min(134,380)=134 | **678 = 容器 ✓** |
| 内屏竖持 669×951 | 669×951 | 357 / 312 | min(193,533)=193 | **951 = 容器 ✓** |
| 内屏横持 951×669 | 951×669 | 507 / 444 | min(274,375)=274 | **669 = 容器 ✓** |

- `columnLeft` 0.5334 + 0.4666 = **100%**，左右列不溢出
- `barW` 下界 240 被 `min(barW, box.width-16)` 兜住，三形态无溢出

**三形态全部「内容高 = 容器高」，永不溢出 ⇒ 不可能形成环。**
