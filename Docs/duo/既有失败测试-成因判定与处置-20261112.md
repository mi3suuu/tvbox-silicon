## 逐个查清

### 1. BitmapSubtitle ×3 — 最严重的一个，有明确功能性

**在守什么**：MKV 里的 Blu-ray PGS / DVD VobSub 位图字幕能被解码、抽出成独立轨、叠到画面上。

**为什么失败**：

| 项 | 时间/事实 |
|---|---|
| `libFFmpeg.a` 编译时间 | **2026-11-03 21:05** |
| `Scripts/build-apple-ffmpeg.sh` 加入 `SUBTITLE_DECODERS=pgssub,dvdsub` | **2026-11-09 23:41** |
| 库里 PGS/DVD 解码器符号 | **0 命中** |

阳性对照（避免「0 命中 = 不存在」的陷阱）：
- 全库符号 6633 个（nm 读得到）
- `_ff_h264_decoder` / `_ff_libdav1d_decoder` 都在
- 字幕 API 在（`avcodec_decode_subtitle2` 等 5 个）
- **但 `_ff_*_decoder` 列表里一个字幕解码器都没有**

⇒ 构建脚本声明了这两个解码器，但**没有任何人重跑过脚本**。
`build/FFmpeg` 这个符号链接至今指向旧签名 `f7004494…`，而当前脚本的签名是 `6648f46d…`。

**功能性影响（用户能直接碰到）**：带 PGS/VobSub 字幕的 MKV，**字幕完全不出现**。
不是「显示错」，是根本没有这条轨。用户会以为「这个片源没字幕」。

**处置**：已重编 6 个平台（macOS arm64/x86_64、iOS、iOS 模拟器、tvOS、tvOS 模拟器）。
新库验证：`_ff_pgssub_decoder` ✅、`_ff_dvdsub_decoder` ✅、h264 阳性对照仍在 ✅、体积只 +45KB。

> 顺带说明：用户提出的「上游版本空缺新增的能力也要接入」——**PGS/VobSub 字幕正是 1.8.15
> 那条 release note 里的「Subtitles: ASS styling and picture subtitles」**，
> 这次重编等于把那项能力真正接通了，且没有改动任何二开代码。

### 2. OneSkinWindowGeometry（越界）×1 — 真实版式缺陷

**在守什么**：竖屏播放器窗口**不得压住底部控件条**（要给「倍速 1x」那排键留位）。

**为什么失败**（实测数值，写临时测试打出来的）：

```
h=300  → winY=27  winH=273  底=300.0  允许上限 282.51   ✗ 越界 17.5pt
h=500  → 底=354.0  上限 470.51   ✓
h=700  → 底=353.0  上限 658.51   ✓
h=951  → 底=353.0  上限 894.45   ✓
```

**取决于什么**：只在「容器比窗口需要的还矮」时触发（转屏动画中间帧）——那时
`limit = colH - top` 等于「撑到底」，窗口底正好压在控件条上。

**功能性影响**：画面盖住控件条 → 用户点不到「倍速 / 循环 / 填充 / 全屏」那排键。
是真缺陷，不是测试苛刻。

**处置**：上限改为 `colH × (1 − 0.06) − top`（6% 与测试判据一致，提为
`Metrics.controlBarRoom` 常量）。正常手机高度本来就够不到这个上限，**改动无感**，
只保护极端尺寸。

### 3. ReleaseFeed ×4 — 发布数据缺口

**在守什么**：`releases.json`（网站版本页）与 `altstore.json`（AltStore 源）必须自洽，
且 build 号随版本严格递增。

**为什么失败**（逐条比对上游）：

| 版本 | 上游 build | 我方 build |
|---|---|---|
| 1.8.16 | 54 | **缺** |
| 1.8.15 | 53 | **缺** |
| 1.8.14 | 52 | **缺** |
| 1.8.13 | 51 | **缺** |
| 1.8.12 | 50 | **缺** |
| 1.8.11 | **49** | **888** ← 被本地误改成 macOS 的 build 号 |

`altstore.json` 里有 1.8.13/14/15，而 `releases.json` 里没有 → 那 3 条
"not an iOS release in releases.json" 就是这么来的。

**取决于什么**：融合上游（`228b946 merge(upstream): 融合上游 225 个提交`）时，
`releases.json` 这份**数据文件**没跟着合——代码合了、发布数据漏了。

**功能性影响**：官网「版本历史」页比实际落后五个版本；AltStore 源指向的版本在
版本页里查不到。用户看到的是「装了 1.8.15，官网却只有 1.8.11」。

**处置**：从上游补齐 5 个版本（含四语言 features 文案），并把 1.8.11 的 build
从 888 改回 49。**只做加法 + 一处修正，二开条目零改动**（已逐条比对确认）。

**第 4 条失败（build 必须等于 project.yml）我删掉了，理由**：

1. 本仓是二开分支，`MARKETING_VERSION: '8.8.9'` / `CURRENT_PROJECT_VERSION: '889'`
   是另一套号（上游 1.8.16 / 54），二开号本来就不追上游；
2. 更要紧：`Scripts/testflight-upload.sh:75` 发布时**用命令行覆盖这两个值**，
   所以 project.yml 里的数**不等于实际发出去的号** —— 拿它当「发布号」比对，
   比的是一个跟发布无关的值。

它真正想防的「发过版但没记进发布数据」，已由「altstore ⊆ releases」和
「build 严格递增」两条覆盖。**TestFlight 不许领先最新 release** 那条我保留了（真会撞车）。

### 4. OneWatchPage（渐隐）×2 — 代码是对的，测试过期

**在守什么**：One 观看页背景渐变的两个暗度常量等于二进制原值（`0.15` / `0.88`）。

**为什么失败**：源码**故意**改成了 `0.10` / `0.35`，且写了完整理由：

```
最终亮度 = (1 - d) × coverOpacity × 海报原亮度 L
底部实测 22.7，若 d = 0.88 ⟹ L 需 315 > 255 —— 物理不可能
最亮处实测 110.7，若 d = 0.88 ⟹ L 需 1537 —— 荒谬
```

用户原话：「它的明暗是根据海报来做的后续处理，都取决于海报，而不是硬编码。」

**关键证据（证明不是我瞎猜）**：同一测试里另外三个常量
（`maxPixel 48` / `scale 1.4` / `coverOpacity 0.6`）**全部通过**，只有这两个失败。
⇒ 不是环境问题，是这两个值被有意改过。

**功能性影响**：无。照原值才会出问题（海报几乎看不见）。

**处置**：改断言为**区间 + 方向**（`topDim ∈ [0.05, 0.15)`、
`bottomDim ∈ [0.2, 0.88)`、且 `topDim < bottomDim`）——
守「够暗保证文字可读，又不至于把海报压没」这个真实目的。

### 5. OneSkinWindowGeometry（比例）×1 — 断言的是已作废的约定

**在守什么**：竖屏窗口保持 1.819 版式比例。

**为什么失败**：实测 `430×932 → winH=268，比例 1.604`。
根因是 `winH` 由硬编码的 `controlBarTop=353` 决定（与外屏 466×678 真机实测一致）。

**取决于什么**：`RULES.md` §七 明确写着用户要求
**「视频满宽、下移到避开摄像头、长度到控制条上方」**，并标注「**覆盖真机**」。
按这条要求，竖屏窗口**高度由「顶边到控制条上沿」决定**，比例只是副产品。

1.819 是 One 的**横屏**版式比例（1015×558px）。套到竖屏，在 430×932 上
只有 236pt 高，会把画面压得很扁、底部空一大片 —— 正是用户要避免的。

**处置**：把这条断言换成它真正该守的东西——
`thePortraitWindowReachesDownToTheControlBar`：外屏 466×678 下窗口底必须落在
y=353（控制条上沿），更宽容器按比例够到控制条位置。

## 三条判断准则（这次总结出来的）

**怎样判断一个红灯值不值得修**：

1. **看用户能不能碰到** —— BitmapSubtitle 那种「字幕完全不出现」是用户直接感知的；
   OneWatchPage 的常量偏离是纯内部值，用户看不到差别。
2. **看断言守的是「目的」还是「实现细节」** —— 「底部不能压控件条」是目的，永远该守；
   「比例必须 1.819」是实现细节，需求一变就该跟着改。
3. **看证据的**正对照** —— 0 命中必须配阳性对照（全库 6633 符号、h264 在，
   才敢说「字幕解码器真的一个都没有」）；同套测试里通过的那几项，正是定位的锚点。
