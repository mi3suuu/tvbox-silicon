# 自查发现的问题（2026-11-10）

审实现代码（下载加速器 + 源测速面板）逐条找出的缺陷，按严重度排列。全部已修并配回归测试。

## P0 — 数据损坏

### 1. lane 写入越界，覆盖相邻区间

`DownloadTransfer.pump` 原实现：

```swift
try sink.write(data, at: cursor.value)
cursor.advance(by: Int64(data.count))
```

未对 `data.count` 做上界钳制。当服务器比请求多返回字节（代理忽略 Range 末端、镜像返回整个文件），cursor 会越过 `range.upperBound`，**把相邻 lane 正在写的区域覆盖掉**。

这是最坏的一类 bug：文件下载"成功"、能播放、中间某段花屏，**任何地方都不报错**。

修复：按本 lane 剩余空间切片。

```swift
let room = range.upperBound - cursor.value
let slice = data.count > room ? data.prefix(Int(room)) : data
```

测试：`aLaneNeverWritesPastItsRange()`

### 2. 不支持 Range 的服务器 → 每次下载必判失败

`fetch(file:)` 新增的完整性校验：

```swift
guard box.plan.files[index].complete() else { throw TransferError.incomplete }
```

但 `complete()` 对 `ranged == false` 恒返回 false（它靠 span 判断，非 ranged 文件没有 span）。而 `ranged == false` 的分支在函数上方已经 `return` 了——问题在于**新建 plan 时若服务器忽返 200 而非 206**，会走到 ranged 路径但 `length == nil`，同样恒 false。

修复：只在可测量时校验。

```swift
if box.plan.files[index].ranged, box.plan.files[index].length ?? 0 > 0 {
    guard box.plan.files[index].complete() else { throw TransferError.incomplete }
}
```

测试：`anUnrangedFileIsNotJudgedByItsSpans()`

## P1 — 资源与正确性

### 3. 描述符双重关闭

`PositionalFile`：

```swift
deinit { if fd >= 0 { _ = close(fd) } }   // ← 检查 fd
func closeHandle() { ... closed = true ... }  // ← 置 closed，但 fd 仍是旧值
```

`closeHandle()` 只置 `closed`、不清 `fd`，deinit 看到 `fd >= 0` 又关一次。**关闭后的 fd 号可能已被内核分给别的 socket**，第二次 close 会误杀不相关连接。

修复：`deinit { if !closed && fd >= 0 { ... } }`

### 4. lane 抢到自己的区间

`RangeQueue.split()` 无参数，可能选中调用者自己持有的区间并切一半塞回队列，随后被同一条 lane 取走 → **重新下载已写完的字节**。计数器还显示"有进展"。

修复：`split(avoid: lane)`，严格排除调用者。曾有"无候选时回退到全体"的写法，同样会切到自己，已删。

测试：`aLaneDoesNotStealItsOwnRange()`

### 5. 孤儿清理删掉正在写的目录

`DownloadLibrary.purgeOrphans()` 按 `items` 判断，把"不在列表里"的目录一律删除。但一个刚开始下载、记录尚未落盘的下载目录也满足该条件 → **从正在 pwrite 的 socket 底下删除目录**。iOS 上表现为"下载完成但 0 字节"。

修复：把 `running` 与 `boxes` 的键视为在用，一并排除。

## P2 — 体验与浪费

### 6. 面板重复全量扫描

`SourceSpeedLab` 的 body 里 `store.answered(targets)` / `silent(targets)` 各出现 6 次，每次 O(n) 遍历所有读数。353 个源 × 12 次/帧，在主线程上。

修复：`buckets` 一次算出四个集合，各段读它。

### 7. "建新组"第二次点不建新组

`file(_:named:)` 用 `createSourceGroup(named:)`，而 `SourceGroupBook.add(name:)` 对同名**复用已有分组**。第二次扫完再点"把可达的建成新组"，会把第二批**并入第一批**，提示却写"12 个已归入 可达"。

修复：名字冲突时加数字后缀。

### 8. 分组消失后面板空转

Scope 选"单分组"时组若被移空/删除，`pickedGroup` 保留一个不存在的 id，所有计数归零且没有任何提示。

修复：`.onChange(of: selectableGroups.map(\.id))` 里回落到第一个。

## 尚未修的已知问题

- **`get()` 与 `pump` 的双层重试**：`get` 内部对同一 range 起点重试 3 次、每个镜像各一次，外层 `pump` 再从 cursor 重试 4 次。最坏情况同一段字节被请求 12 次。**不会写坏**（同 offset 覆盖），但会浪费带宽。合并成单层重试需要重构 `get` 的镜像选择语义，暂不动。
- **面板渲染未做真机验证**（无点击注入工具）。
- **`routeByReachability` 对 hidden 源也生效**：`automaticSites` 已排除 hidden，所以当前 scope 下不会命中；但若将来把 scope 扩到含 hidden，需要再过滤。

## 重试叠加（原 P2 遗留）— 已处理，但结论与原估计不同

原文写的是"最坏同一段字节被请求 12 次"。**实测推翻了这个数**，连同我修它的第一版一起记下来。

### 实测：无故障基线是 2 次

1 MB 文件，服务器不限速不故障，跑完整下载：

```
OK 1 bytes=0-0          ← TVBoxProbe --bench-download 自己的前置探测，不在下载器里
OK 2 bytes=0-65535      ← prepare 的 head 探测（下载器）
OK 3 bytes=0-1048575    ← fetch 的 chunk（下载器）
```

**单次下载 = 2 个请求。没有浪费。**

### 实测：2 次 503 时是 6 次

```
FAIL 2,3 bytes=0-65535      head：get 内 3 attempt
OK   4 bytes=0-65535
FAIL 5,6 bytes=0-1048575    chunk：get 内 3 attempt
OK   7 bytes=0-1048575
```

每段 3 次（get 的 3 attempt），不是 12 次。**pump 的重试在正常路径上从未触发**，因为 `get` 的 3 次已经把 2 次 503 消化掉了。原"12 次"是理论最坏值（pump 4 x get 3），需要一个 3 次以上 503 的服务器才会接近。

### 第一版修复是错的，把健壮性改坏了

我删掉 pump 的重试，让 `get` 独占：结果**连续 5 次 503 从"能恢复"退化成"必然失败"**。

```
connections=1 chunk=1MB 6.10s status=failed   ← 5 次 503
```

`get` 只有 3 attempt，第 4 次 503 就超出预算，而这个错误浮到 pump 时无人接。这是"减少重复"换来的真实功能倒退。

### 最终形态：预算明确，各层只做自己的事

| 层 | 负责 | 预算 |
|---|---|---|
| `get` | 镜像轮换 + 瞬时故障 | 3 attempt x 每个镜像 |
| `pump` | 短交付（连接正常结束但没给满）+ 超出 `get` 预算的失败 | 2 次，退避 800ms x n |
| 合计上限 | | 5 次/区间（单镜像） |

### 修复后实测

```
fail_first=5:
  head : FAIL x5 + OK   → 5 次（get 3 + pump 2，正好用满）
  chunk: FAIL x5 + OK   → 5 次
  结果：completed
```

旧形态同样场景要 7 次（pump 4 叠加 get 3）。现在 5 次达到同样结果。

### 1 GiB 回归

```
connections=1  300.02s  0.76 MB/s
connections=8  168.22s  6.09 MB/s  peakSockets=8  completed
```

与改动前 168.06 s / 6.09 MB/s 一致，无性能退化。

### 判据

`theRetryBudgetDoesNotMultiply()` 把算术固定下来：新形态 ≤6 次上限、旧形态 12 次，断言新 < 旧。

### 教学

**"最坏情况"不能用理论乘法代替实测。** 我按 4x3 算出 12 次并据此动手，实测基线是 2 次、2 次 503 时是 6 次——问题比想象的小得多，而我的"优化"反而砍掉了真实需要的冗余。改之前先测当前真实值。
