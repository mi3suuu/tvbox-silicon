## 二、五条裁决规则（按顺序适用，先命中先生效）

**R1｜上游新增的独立能力 → 全量采纳上游。**
上游这 374 个提交里有大量我方完全没有的新能力（小说阅读器 Legado、直播插件平台与扫码登录、
彩色主题、App 图标选择器、百度/天翼/123/光鸭/飞牛网盘、字幕全链路 libass+PGS、片头片尾跳、
豆瓣评分、弹幕服务中心、节目单、追剧日历……）。这些不是我方二开领域，上游怎么来就怎么来，
**不要为了「统一风格」去改上游新代码**。

**R2｜我方登记在案的能力 → 保留我方，并把上游对该处的新改动并进去。**
判据：`Docs/fusion/03-侵入点登记表.md` 的 I-01 ~ I-42。凡冲突处落在登记范围内，
默认保留我方语义，然后把上游这一处的**新增部分**（新参数、新分支、新状态）补进来。
典型：`EpisodeSkip`（我方广告段 `blocksAds` + `episode` 两参数）、`PlaybackHistory`（我方 `environment`）、
`SourceGroups`（我方 `Kind.other` + 两个默认参数）、`MediaCache`（我方 `persist(force:)`）、
`ScriptRuntime`（我方代理会话）、`VideoEnhancement`（我方 `enabled` 总开关）。

**R3｜双方改同一处、语义不互斥 → 两边都要在，且我方在前。**
最典型是本地化文件与列表型 switch。上游把「Downloads」整套改名成「Offline Cache」
（`Notifications`/`Downloads` 全链路），我方二开在旧名上还有入口 —— 这种要**两套 key 都在**，
不能因为「上游改名了」就删我方 key。

**R4｜函数签名变了 → 以上游新签名为准，改我方调用点。**
已知上游这轮改了签名的（必须跟着改调用方，不许保留旧签名做重载凑合）：
- `CloudSources.fetch(http:address:)` 新增 `address:`
- `CloudBufferPlan.make(length:duration:budget:chunkSize:)` 去掉了 `share:`
- `ScriptRuntime` 新增 `Jars` 类（按 `jar` 名共享 cookie），旧的按 proxy 缓存会话仍在
- `ScriptAssets/tvbox/prelude.js` 新增 `account(request, input)` 方法分发，我方 `warm` 分支要保留

**R5｜品牌与身份一律取我方。**
`Yingxia` → 「顾及One」/`Mi3s`；`INFOPLIST_KEY_CFBundleDisplayName`、`Localizable.strings` 里的
品牌串、App 图标（我方 `Design/icon-sources/` 自绘四态）、`YingxiaLogo.imageset` 全是品牌资产，
**上游这些位置的改动一律不采纳**（上游改名、换 8 个新图标、删除旧 logo 都不跟）。
