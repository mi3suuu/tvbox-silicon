# 25 · 点播源：批量操作、按结果分组、分组优先级

日期 2026-11-11 · 分支 `fusion/restructure-A` @ `5a9ff94` + 工作区改动（未提交）

## 要解决的问题

点播源页（`App/SitesView.swift`）此前只能一个个点：一张卡片一个右键菜单，一个分组一个拖放目标。
真实场景是 100–350 个源、6–12 个分组，于是四件事做不了：

1. 分组一多，把页面折起来要逐个点头标。
2. 测完速想把「连得上的」归一组、「连不上的」归一组，只能拖。
3. 想只测某个订阅、只测某个分组，入口要绕去设置里的另一页。
4. 「先搜哪个源」只能靠拖动 300 行排序；分组这一层完全没有话语权。

## 一、批量写入为什么不能逐个调

`Store.reassignSource` 末尾无条件 `rebuildSubscription()`，而后者重建整张合并表（分类每个源、
重跑路由、重新分区隐藏/置顶）。移动 300 个源就是 300 次全量重建——这是这个功能此前没人做的
真实原因，不是界面没画。

修法是加一把**只影响缓存刷新、不影响存储内容**的闸门：

```swift
@ObservationIgnored var suppressRebuild = false   // Store.swift
// reassignSource: if !suppressRebuild { rebuildSubscription() }
func performBatch(_ body: () -> Void)             // Store+SourceGrouping.swift
```

`performBatch` 里跑完所有 `reassignSource`，退出时统一重建一次。**存的东西一样**：每条 move 仍
由 `SourceReassignment` 逐条记录，所以「移回原订阅」页的「全部放回」照样能一把撤销一批，
订阅刷新也照样保得住。

`fileSources(intoGroup:)`、`fileSources(underSubscription:)`、`returnSourcesToTheirSubscription`
三个既有批量函数一并改成走 `performBatch`——它们原本也是 O(n) 次重建。

## 二、按结果分组的口径（两条硬规则）

`fileByReachability(_:into:silentGroup:)`：

- **没有读数的源两边都不进**。把没测过的源当死的归档是猜；比「慢」更糟的是「能用的被藏进不通」。
  返回 `unknown` 计数，界面照实说「还有 N 个未测速」。
- **同名分组存在就并进去，不另起一个**。同一天测两次订阅，读者想的是把新结果并进昨天那个组，
  不是长出一排「可连 2 / 可连 3」。要真正新建一个组，选择条里有明确的「新建分组…」。
  测速页的按钮文案随状态切换（「新建分组」↔「归入已有分组」），按的是事实而不是猜测。

旧的三参数形式 `fileByReachability(_:reachableName:unreachableName:)` 保留为薄转发，
两处旧调用（测速页、`SourceSpeedTestView`）行为不变。

## 三、搜索顺序里的分组维度

`SourceOrder` 新增第二条列表 `preferredGroups`：

```swift
public func arrange(_ sites: [Site], origin: URL, group: (Site) -> String) -> [Site]
```

一个比较器同时比「组序」和「源序」，不是两趟排序——两趟会在第二次排序里把组的桶打散。
组序在前、源序在其内破平，所以给六组排序不会丢掉已经手工调过的 300 行。

三条设计取舍：

- **组序与「自定义源顺序」开关解耦**。组序一设就生效；源序仍只看自己的开关。理由是两者粒度
  不同：排六个组是任何人都会做的决定，排三百行是要花一小时的活。
- **没排过序的组排在所有排过序的组之后，而不是被丢掉**。「还没排」不等于「请忽略这个源」。
- **页面上的分组位置不动**。想让某个订阅先被搜索，并不等于要求它的分区跳到页面顶部。
  组序只作用在搜索（`SearchModel.arrange`），页面顺序仍由拖标题头 / `moveSourceGroup` 决定。

`SearchModel` 通过 `Store.groupID(listing:)` 拿到每个源所在组的 id，读的就是页面画出的那份
缓存分组，所以不可能与用户看到的目录不一致。

搜索的取用顺序（`SearchModel.run`）保持原样：内置源优先、用户顺序生效时按用户顺序、失败源最后。
组序在 `arrange` 内部完成，不新开一层。

## 四、界面为什么这样摆

- **一键折叠放在列表顶部，不放在工具栏。** 手机导航栏已经有过「第二个 `.primaryAction` 被静默
  丢掉」的先例；更要紧的是「折叠全部」是被折叠那张列表自己的属性，控制件压在它自己的列表上方
  不需要解释。它同时是页面上唯一说明「一共几组、几个源」的地方——不知道有几组就不会想到要折叠。
- **选择条在列表最上面，不浮在底部。** 底部浮条会遮住正在勾的那一行。
- **选择模式下整张卡片就是勾选框**，点哪都不跳转。这是本页唯一「点了不进去」的时候，而选择条
  已经写明此刻在做什么。
- **分组头右侧给「本组勾选 / 取消」**。组是用户自己整理出来的批次，「这一组全要」远多于逐个点。
- **批量动作全在一行**：分组 / 隐藏 / 置顶 / 测速 + 一个「更多」（按结果分组、按可达性路由、取消置顶）。
  分散到多个菜单就要读者记住哪个菜单装哪个——正是这一页要消掉的成本。
- **隐藏是一个按钮两个方向**：全已隐藏则按下去是「显示」。它描述的是这批源的状态，不是两个不相干的功能。
- **移动完成后清空勾选**。卡片已经去了别处，留着勾选会让第二次按下重复移动同一批，那从来不是任何人的意思。

## 六、子代理并行审查：查出并修掉的 12 处缺陷

四个子代理并行静态推演各自负责的改动（SitesView 选择/折叠、批量写入语义、测速页作用域与文案、源序与分组优先级）。
**它们各自查出了我自查漏掉的真缺陷**，其中 2 处为 blocker/high，会让功能完全不生效或数据落错地方。

| # | 严重度 | 谁查出 | 问题 | 修法 |
|---|---|---|---|---|
| 1 | **blocker** | 审批量写入 | 页面传 `CustomSourceGroup.id`（裸 UUID），而 move 的 target 是 `group:<id>`；`SourceGroups.make` 只认后者 → 整批源落进「Other Sources」，界面却报「已移动 N 个」；不可解析的 target 还会持久化 + 随 iCloud 同步，Moved Sources 页显示 missingTarget | 新增 `Store.moveTarget(named:groups:)` 归一化，页面只需交出它自然持有的 id |
| 2 | blocker（同根旧疾） | 审批量写入 | 拖拽卡片到自定义组头也一样传裸 id —— HEAD 就有，即「菜修好了、拖拽还坏」 | 新增 `reassignSourceByKey(_:origin:groupID:)`，拖拽路径改用它 |
| 3 | **high** | 审 SitesView | `SourceSpeedLab(picked:)` 传了源，但 `scope` 默认仍是 `.all`，全仓无人设成 `.picked` → 勾 12 个点测速，实际把 300 个源全扫一遍，注释宣称的交互完全没实现 | `.task` 里 `if !picked.isEmpty { scope = .picked }` |
| 4 | **high** | 审 SitesView | `Select All Shown` 用赋值 `selection = Set(visible)`，搜索后一点就**静默取消屏外勾选**，与操作条「计数含屏外」的语义正相反 | 改 `formUnion` |
| 5 | **high** | 审源序 | 编辑器 `groups` 过滤空组后当 `among` 传给 `moveGroup` → 任何一次箭头操作都会**把空组从排序里静默删掉**，与 `pruneGroupOrder` 明确保留的口径相反 | 编辑器不再过滤空组；`ranked` 改用「id 是否在已排列表里」判断，不用序号比较 |
| 6 | **high** | 审源序 | `moveGroup` 的 `order` 在已排序时只含已排子集 → 「已排区最后一名按下移」算出 `to == from` 直接 return，**按钮点了没反应**（同位置上移却正常） | 始终以完整 `known` 列表为工作集 |
| 7 | medium | 审源序 | `pruneGroupOrder` 的 `known` 含**已关闭**订阅的地址（而 `SourceGroups.make` 只给启用的建组）→ 死 id 永久占位 | 只取 `filter(\.enabled)` |
| 8 | medium | 审测速页 | 四档文案塞进 `.segmented`，窄屏「One Subscription / 手选的源」必截断 | 改菜单式 Picker |
| 9 | medium | 审测速页 | **两条探测路径的 origin 语义不一致**：`.all` 走 `probeTargets` 统一用 `config.origin`（= 合并后**第一条**订阅的 origin），其余档用 `site.origin(or:)` → 多订阅时第 2 个及以后订阅的源按错 host 解析 API，好源被判「不可达」 | `probeTargets` 改用 per-source origin |
| 10 | medium | 审测速页 | 用**本地化后的组名**当组身份：切语言后找不到上次建的组，`add(name:)` 又按名匹配 → 长出两个「可连接 / Reachable」各持一半 | `L10n.everyRendering(of:)` + `alsoMatching/silentAliases`，四语名任一命中即复用同一组 |
| 11 | low | 多处 | 死代码/残渣：`addAnother(named:)`、`arrangeGroups(_:)`、`let style = compact`、`named:` 死参数、4 条孤儿本地化 key | 全部删除 |
| 12 | low | 审源序 | `sourceOrder.groups.v1` 未进整机备份白名单 → 「备份→换机恢复」丢分组排序，而 iCloud 又能带回来，两条恢复路径结论不一致 | 加入 `FullBackup.dataKeys` |

自查另修（子代理未提或提了但我先发现）：
- `answered()` 用 `!= .unreachable` 把**「没有读数」和 `.unknown` 读数都算作可连**，与该函数自己上一段注释直接矛盾，且让「未测速」计数恒为 0 → 改显式 case 列表。
- `fileByReachability` 无 `.unknown` 分支，未测源被当「可连」→ 单列 unknown。
- 三个批量改派口无 `where !site.isBuiltIn`，计数虚高（内置源被 `reassignSource` 静默拒绝）→ 统一过滤。
- `setRoute` / `setHidden` / `setPinned` 的计数与重建：批量路由每次重建 2 次 → 全部走 `performBatch`；隐藏/置顶返回真实变更数而非 `sites.count`。
- 选择模式原先 `collapsed = []` 后 `foldState.save` 会**永久改写**用户的折叠偏好 → 改为进入时备份、退出时还原。
- `SearchModel.arrange` 在有组序时无条件读 `keys` 破平 → 关掉自定义源顺序后仍按旧手序排，加 `enabled` 闸门 + 回归测试。
- 一键折叠丢了旧控件的 `disabled(!query.isEmpty)` 守卫；`listControls` 的「N 源」与「N 组」口径不一致（一个含 hidden 组）。
