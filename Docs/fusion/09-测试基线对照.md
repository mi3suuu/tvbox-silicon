# 测试基线对照（融合版 vs 纯上游）

> 目的：坐实「融合没有引入任何测试失败」。任何「失败了」的结论必须先跟纯上游基线对照，
> 否则会把上游自带的问题算成融合回归 —— 这正是本项目最贵的教训（旧代码标「实测通过」但有隐形 bug）。

---

## 一、对照方法

同一个 SwiftPM 包（`Packages/TVCore`），同一台机器，同一条命令：

```bash
swift test --package-path Packages/TVCore
```

| 树 | 内容 | 路径 |
|---|---|---|
| **融合版** | `22180e4` 上游 + 全部二开能力 | `tvsilicon/tvbox-silicon-fusion`（`fusion/main`） |
| **纯上游基线** | `22180e4`，零二开 | `tvsilicon/tvbox-wt-baseline`（`fusion/base`，独立 worktree） |

---

## 二、结果对照（2026-11-06 实跑）

| | 融合版 `fusion/main` | 纯上游 `fusion/base` |
|---|---|---|
| 测试总数 | **766** | **589** |
| 失败数 | **4** | **4** |
| 失败集 | 见下 | **完全相同** |

### 失败清单（两棵树逐项一致）

| # | 测试 | 失败原因 | 判定 |
|---|---|---|---|
| 1 | `JavaHostVersionTests.javaHostVersionChangesWithTheConverter()` | `manager.enumerator(atPath: java/com/googlecode)` 返回 nil —— `Runtime/JavaHost` 产物不在 SwiftPM 包内 | 仓库布局问题，与代码无关 |
| 2 | `FeedbackAttachmentsTests.feedbackSizeLimitsMatchTheServer()` | 读不到 `Packages/TVCore/Services/error-reports/src/index.ts` —— `Services/` 同样在包外 | 仓库布局问题 |
| 3 | `RemuxTests.hevcInTransportStreamHLSPlaysRepackaged()` | `played.status != .readyToPlay`（10s 超时） | **并行资源竞争**（见下） |
| 4 | `RemuxTests.liveHEVCInTransportStreamFollowsItsPlaylist()` | 同上 | 同上 |

### 关于 3/4 两条（关键，别误判成融合 bug）

这两条**单独跑能过**：

```bash
swift test --package-path Packages/TVCore \
  --filter "hevcInTransportStreamHLSPlaysRepackaged|liveHEVCInTransportStreamFollowsItsPlaylist"
# → Test run with 2 tests in 1 suite passed
```

但在全量 `swift test` 里必失败，**纯上游基线同样如此**。原因：这两个用例要起本地 `RangeServer`（HTTP）+ 真 AVPlayer 解码，全量跑时与其他 Remux/网络用例抢端口与解码资源，10 秒超时不够。

**我还验证过一次误导性现象**：当我用我方版 `RemuxPlan` 时，这两条失败；换回上游版后仍失败 —— 一开始把这当成「我方重构有问题」，其实只是并行竞争。后来单跑才澄清。这就是本文件存在的理由。

> 教训：**光看「换成 X 之后失败了」不能定因**，要么单跑，要么拿纯上游基线全量跑一遍对照。

## 五、补充：Java / Native 测试也要跑一遍才知道能不能过（2026-11-06 第 3 轮）

前几轮只跑了 `swift test`（TVCore，783 项）。但仓库还有两套**完全不经过 SwiftPM** 的测试：

| 套件 | 位置 | 驱动脚本 | 前置产物 |
|---|---|---|---|
| Java host | `Tests/Java/` | `Scripts/test-java-host.sh` | `build/JavaHost/{host.jar,lib/*}` |
| Native bridge | `Tests/Native/` | `Scripts/test-apple-runtime-bridge.sh` | `build/AppleRuntime/` |

### 实际跑出来的两个问题

**一、`host.jar` 是旧产物（已解决）**

`Scripts/test-java-host.sh` 编译报 7 个错，全是 `DexClassLoader.pluginClass/guestClass` 找不到符号。
查证：方法**存在于源码**（`Runtime/JavaHost/src/main/java/dalvik/system/DexClassLoader.java:25/48`），
但 `build/JavaHost/host.jar` 是旧构建。跑 `Scripts/build-java-host.sh` 重建后：

```
javap -classpath build/JavaHost/host.jar dalvik.system.DexClassLoader
  public static java.lang.Class<?> pluginClass(java.lang.String);
  public static java.lang.Class<?> guestClass(java.lang.String);
```

> 注意：**不能用文件时间戳判断 jar 是否最新** —— `git checkout` 会把源码 mtime 重置到 checkout 时刻，
> 实测出现过「jar 比源码新但内容旧」。判据只能是 `javap` 查实际成员，或直接重建。
> `build/` 在 `.gitignore` 里，所以过期的 jar 不会被提交，纯粹是本机产物没跟上。

**二、`HostCompatibilityTest.pluginKeepsItsOwnSlf4j` 失败（上游自带，未修）**

```
java.lang.ClassNotFoundException: org.slf4j.impl.SimpleLoggerFactory
	at HostCompatibilityTest.pluginKeepsItsOwnSlf4j(HostCompatibilityTest.java:94)
```

根因是**包路径代际错配**：

| | 实际路径 |
|---|---|
| 测试要的 | `org.slf4j.impl.SimpleLoggerFactory`（slf4j **1.x** 布局） |
| 项目用的 | `slf4j-simple-2.0.13.jar` → `org.slf4j.simple.SimpleLoggerFactory`（**2.x** 挪了包） |

**判定为上游测试问题，不是融合引入**，证据：

1. `diff` 两份 `Tests/Java/HostCompatibilityTest.java`（基线 vs 融合）→ **完全一致**
2. 该文件来自上游提交 `dabbc2a "Java host: make the aowu.json plugins work on iOS"`

**处理：不改**。理由 —— 这是上游的文件，按本项目铁律「上游文件是别人的文件」不动它；
改它会给下次对齐上游多造一处冲突面。要在`02-未纳入清单.md` 里登记为已知上游缺陷。
