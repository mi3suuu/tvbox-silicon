### 实际跑出来的两个问题

**一、`host.jar` 是旧产物（已解决）**

`Scripts/test-java-host.sh` 编译报 7 个错，全是 `DexClassLoader.pluginClass/guestClass` 找不到符号。
查证：方法**存在于源码**（`Runtime/JavaHost/src/main/java/dalvik/system/DexClassLoader.java:25/48`），
但 `build/JavaHost/host.jar` 是旧构建。跑 `Scripts/build-java-host.sh` 重建后：

```
javap -classpath build/JavaHost/host.jar dalvik.system.DexClassLoader
  public static java.lang.Class<?> pluginClass(java.lang.String);
  public static java.lang.Class<?> guestClass(java.lang.String);
```

> 注意：**不能用文件时间戳判断 jar 是否最新** —— `git checkout` 会把源码 mtime 重置到 checkout 时刻，
> 实测出现过「jar 比源码新但内容旧」。判据只能是 `javap` 查实际成员，或直接重建。
> `build/` 在 `.gitignore` 里，所以过期的 jar 不会被提交，纯粹是本机产物没跟上。

**二、`HostCompatibilityTest.pluginKeepsItsOwnSlf4j` 失败（上游自带，未修）**

```
java.lang.ClassNotFoundException: org.slf4j.impl.SimpleLoggerFactory
	at HostCompatibilityTest.pluginKeepsItsOwnSlf4j(HostCompatibilityTest.java:94)
```

根因是**包路径代际错配**：

| | 实际路径 |
|---|---|
| 测试要的 | `org.slf4j.impl.SimpleLoggerFactory`（slf4j **1.x** 布局） |
| 项目用的 | `slf4j-simple-2.0.13.jar` → `org.slf4j.simple.SimpleLoggerFactory`（**2.x** 挪了包） |

**判定为上游测试问题，不是融合引入**，证据：

1. `diff` 两份 `Tests/Java/HostCompatibilityTest.java`（基线 vs 融合）→ **完全一致**

**处理：不改**。理由 —— 这是上游的文件，按本项目铁律「上游文件是别人的文件」不动它；
改它会给下次对齐上游多造一处冲突面。要在`02-未纳入清单.md` 里登记为已知上游缺陷。

## 七、Java host 版本门禁（2026-11-06 第 9 轮）

上游脚本 `Scripts/check-java-host.sh` 专门防一件事，值得记下来：

> Xcode 会把 `build/JavaHost`（Mac）和 `build/AppleRuntime/<platform>/Resources/JavaHost`
> **原样拷进 App，不重新构建**。所以一个过期的 host.jar 会把旧的 DEX 转换器带上设备。
> 上游注释里写了实际事故：2026 年 10 月一份 host-v13 的副本，让「玩偶哥哥」等 2026-10-21 FTY jar
> 的源在**所有设备上全空**，而 main 上早就有修复。

判据是 `BytecodeCompatibility.VERSION`（`host-v19`）：转换逻辑一改它就升，打包的 jar 必须带着同一个。

### 本轮实跑

```
源码     host-v19
产物     5 个（Mac 1 + 三个 Apple 平台各 1）
不符     0 ✓
```

另外把 `build/` 下所有历史 DerivedData 里的 host.jar 也扫了一遍（46 个），**全是 host-v19**，
没有陈旧产物残留。

### 这一条为什么重要

它和第 3 轮踩的那个坑是同一类：

| 第 3 轮 | 第 9 轮 |

| `build/JavaHost/host.jar` 缺 `pluginClass`/`guestClass` | 同样性质的「产物过期」 |

## 八、本地化检查（2026-11-06 第 10 轮）

跑上游脚本 `Scripts/check-localizations.py`，红了：

```
AssertionError: English source drift: Filter Type
```

### 先判来源：不是融合引入

纯上游基线 `tvbox-wt-baseline` 上跑同一个脚本，**挂在同一处**。
`en.lproj` 里 `"Filter Type" = "Type"` 在 `22180e4` 就是如此。这是上游自带的 5 条 en 漂移
（`Filter Type` / `Filter Genre` / `Catalog Series` / `Tap to check` / `Extra Requests Warning`）。

登记 **UP-03**，不改上游表。

### 绕过这条后，查出两个真问题

**一、17 个 key 代码在用、en 表没有**

英文用户会直接看到 key 原文。分两批：

| 来源 | 条数 | 例子 |
|---|---|---|
| 云备份（W2） | 14 | `Backups` / `No Backups Yet` / `Restore from Cloud Drive` |
| 隐私保险库（W1） | 3 | `This source is hidden. Unlock the Privacy Vault to browse it.` |

查证：旧仓库 `import/ours` 的 en 表**同样没有**这 14 条 —— 是历史遗留，不是本轮新增。
但保险库那 3 条是**所有语言都缺**，属于真遗漏。

处置：四语言各补齐，现在 `en = zh-Hans = zh-Hant = ja = 1791` keys，键集零差异。

**二、`Playing %@ in %d s` 参数顺序颠倒（我方新增，真 bug）**

```swift
Text(L10n.text("Playing %@ in %d s", target.video.name, remaining))
// 传入顺序：名称, 秒数
```

| 语言 | 原译文 | 运行时实际显示 |
|---|---|---|
| zh-Hans | `"%d 秒后播放 %@"` | 「**某剧名** 秒后播放 **5**」 |
| ja | `"%d 秒後に %@ を再生します"` | 同上 |

上游 `22180e4` 没有这条 key —— **是我方引入的**。

修法：改用位置化占位符，与参数顺序解耦：

```
zh-Hans  "%2$d 秒后播放 %1$@"
zh-Hant  "%2$d 秒後播放 %1$@"
ja       "%2$d 秒後に %1$@ を再生します"
```

> 位置化写法还有个附带好处：翻译者可以自由调整语序，不会再把参数位置搞错。

### 最终对照

| 项 | 纯上游基线 | 融合版（修复后） | 判定 |
|---|---|---|---|
| 键集一致 | ✅ | ✅ 1791×4，零差异 | 已修 |
| 空翻译 | 0 | 0 | — |
| 代码引用缺 key | — | 0 | 已修 |
| 格式失败（上游判据） | **6**（2 key × 3 语言） | **6**（同一批） | 上游自带，未增加 |
| en 漂移 | **5** | **5**（同一批） | 上游自带，未增加 |

### 一处判据缺陷（记下来）

上游脚本的格式判据 `%(?:\d+\$)?[...][@dDiu...]` **不认位置化 `%1$@`**，
还把 `60% of` 里的 `% o` 当成八进制格式符。所以这两类永远是假阳性：

- `Keep at least 60% of the video as main content.` → 误判 `% o`
- 任何用 `%1$@`/`%2$d` 的译文 → 误判「格式不符」

**这不影响我的修复正确性** —— 位置化占位符在 `String(format:)` 里完全合法，
只是上游脚本的正则没覆盖。若将来要让它全绿，得同时改那条正则和 5 条 en 漂移，两处都是上游文件。

### 四、踩到的格式坑（记下来）

`audit-source-loading.py` 要的快照格式，第一版我写错了两次：

```python
# 错法 1：sites 里直接放裸 site
{'sites': [site, ...]}          # → KeyError: 'raw'

{'sites': [{'raw': site}]}      # → 仍缺顶层 raw，plugin 解析拿不到 spider

# 对法：顶层 raw = 订阅里除 sites 外的内容；sites[i] = {'raw': 单个 site}
{'origin': url,
 'raw': {spider, hosts, rules, lives, ...},   # 顶层
 'sites': [{'raw': site}, ...]}
```

关键在脚本第 30 行 —— 它用 `config['raw'].get('spider','')` 取**订阅级**的 spider 路径，
所以 `raw` 必须是订阅对象，不是单个 site。

```
Hongguo    ✅ 24 videos / 7 categories     ← 修好了
Xifan      ✅ 30 videos / 39 categories
Hema       ✅ 10 videos / 126 categories
```

### 根因：`host.mjs` 少了 `random` op

`Runtime/ScriptHost/host.mjs` 的 crypto 分派只有 4 个 op：

```
aes / inflate / hash / hmac / pow
```

而 `builtin.hongguo` 的 js 里调用 `{ op: "random" }` → 落到 `throw new Error('unsupported crypto operation')`
→ 整个源初始化失败。

**关键点：Swift 侧早就支持了。** `Sources/TVCore/ScriptCrypto.swift:54` 就有 `case "random":`
（用 `SecRandomCopyBytes` 取随机字节）。两边不一致。

为什么影响真机：`LocalJarHost.swift:14` —— 当 App 打包了 `ScriptHost/node` 时，
`.javascript` 源走 **node 路径**（host.mjs），不走 Swift `ScriptCrypto`。所以真机上一样会挂。

### 修法

`Runtime/ScriptHost/host.mjs` 补一个分支，参数与返回格式对齐 Swift 侧：

```js
if (request.op === 'random') {
    const count = Number(request.count);
    if (!Number.isInteger(count) || count < 1 || count > 1024) throw new Error('invalid random byte count');
    return { data: crypto.randomBytes(count).toString('base64') };
}
```

已标 `// [mi3s]` 并说明为什么加 —— 这是**补上游缺口**，不是改上游语义。
登记进 `03-侵入点登记表` 作 `I-25`。

### 顺带发现的两个环境坑（不是代码问题）

**一、`build-script-host.sh` 只拷 `node`，不拷它依赖的 dylib**

Homebrew 的 node 动态链接 `libnode.147.dylib`，脚本 `cp "$NODE" "$DEST/node"` 拷完就断了：

```
dyld: Library not loaded: @rpath/libnode.147.dylib
```

规避：手工 `cp /opt/homebrew/Cellar/node/<ver>/lib/libnode.147.dylib build/ScriptHost/`。
上游脚本假设的是自包含 node 二进制，Homebrew 版不是。

**二、`rm -rf` 不干净会导致补丁静默不生效**

第一次改完 `host.mjs` 后重建，报 `cp: build/ScriptHost/node: Permission denied`，
`build-script-host.sh` 中途退出 —— **`host.mjs` 的副本没更新**，重测评测还是旧行为。
差点误判成「补丁无效」。

教训：`build-script-host.sh` 是 `set -euo pipefail`，任何一步失败就停；
改完必须**核对构建副本里真的有那个改动**（`grep -c` 目标文件），不能只看源码改了。

| `mp4` | 前 16 字节含 `ftyp` |

### header 是决定性的（一次实测）

同一个地址，不带 / 带 UA+Referer：

```
虎牙js   裸=200   带头=206   ← header 救了
厂长     裸=206   带头=206   两者都 OK
```

但带 header 也只把**状态码**从 200 变成 206，
`虎牙js` 的内容仍是 HTML —— 所以脚本做了两级判：
先判内容，内容不像媒体时才去试 header，再判一次内容。

### 这条教训比数字重要

前两轮我一直在改判据的**形状假设**（vod_name 非空、url 是字符串），
这一轮遇到的是更根本的：**把「接口返回了东西」当成「这个功能可用」。**

`need sign info`、`404 Not Found`、HTML 网页，全都是「返回了东西」。
真正的判据只有一个：**拿到的东西能不能喂给播放器。**

### 我方 4 源用新判据重验：只有 1 个真能播

第 13 轮说「播放 3/4」，那 3 个当时只验了「有 url」。用新判据重跑，**结论要改**：

| 源 | 有地址 | 内容 | 判定 |
|---|---|---|---|
| Xifan | ✅ | mp4 | **真可播** |
| Bilibili | ✅ | HTML | 不是媒体 |
| Hema | ✅ | 空响应 | 不是媒体 |
| Hongguo | ❌ | — | 源站限制（已用基线坐实） |

`真·可播 1 / 有地址 3`。

Bilibili 返回 HTML 这件事值得单说：它的地址是
`cn-*.bilivideo.com/upgcxcode/…m4s`，看着像正经 CDN 分片地址，
直接 GET 却返回网页 —— 因为 B 站的 m4s 需要带 Referer + 特定 UA 才给数据。
App 侧会带（`Catalog` 里有 header 拼接逻辑），脚本这一层没带全。

## 十四、三个实现 bug 让「能播」被低估了一倍（2026-11-06 第 16 轮）

上一轮我说「真可播 4/48」。这轮修完三个**自己写的 bug** 后，是 **8/48**。
上一轮的数字一半是假的 —— 不是源变好了。

### bug 1：`-w` 状态码解析错位

```python
cmd = ['curl', ..., '-w', '\n%{http_code}']
out = subprocess.run(cmd + [url], capture_output=True).stdout
body, _, code = out.rpartition(b'\n')      # ← body 里也有换行
```

二进制响应（mp4）里到处都是 `\n`，`rpartition` 切到的是**最后一个换行**，
状态码能对上，但 `body` 只剩最后几十字节 —— 分类器自然判不对。

`need sign info` 那次能对上纯属巧合（纯文本没有内嵌换行）。

改成显式分隔符：

```python
'-w', '\n---STATUS:%{http_code}---'
marker = b'\n---STATUS:'
body, _, tail = out.rpartition(marker)
```

### bug 2：分类器先判文本，把二进制当 HTML

```python
head = blob[:200].lstrip().lower()
if b'<head' in head[:100]: return 'html'   # ← mp4 里含 'hdlr'/'stsd'/'avc1'
```

实际抓到的响应尾部是：

```
...avc1...stsd...hdlr...VideoHandler...vmhd...---STATUS:206---
```

**真视频，被判成 html。** 判据顺序必须「先认二进制魔数，再判文本」：

```
#EXTM3U → hls
ftyp(前16) → mp4
0x47 双包 → mpegts
avc1/avcC/moov/mdat/stsd/hdlr/stbl → isobmff
之后才轮到 html / text-error
```

### bug 3（最严重）：把截断的展示用 URL 传去验证

```python
head = raw_url[:120]          # 展示用，截断
rec['play']['verified'] = verify_now(head, hdr, p)   # ← 传错了
```

B 站真实地址 **713 字符**，截到 120 后签名不完整 → 必然 403。

这个 bug 伪装得极好：连续三轮我都以为是「B 站签名有时效」，
因为手工 curl 完整地址永远是 206。直到把 `verify_now` 的实参打出来才看见：

```
A) verify_now(完整 url)  → mp4 / 206
C) verify_now(截断120)   → html / 403
```

### 修正后的真实数字

**演示订阅 48 源**

```
总源数        48
  有播放地址   19
  真·可播       8   ← 17%，全部 hls + http=206
```

8 个里 6 个是 `127.0.0.1:PORT/…/media?do=m3u8&url=…` ——
**App 内置代理确实在工作**（代理转出 HLS 清单，206）。上一轮把它们判成「假象」是错的。

**我方 4 源**

```
Bilibili  mp4  206  ✓
Xifan     mp4  206  ✓
Hema      mp4  206  ✓
Hongguo   —    —    源站限制（第 13 轮已用基线坐实）
真可播 3/4
```

上一轮说「我方只有 1 个真能播」也是 bug 3 造成的误判。

### 教训

前 15 轮我一直在修「判据的语义」——该看什么、不该看什么。
这一轮是**判据是对的，实现写错了**，而且三个 bug 互相叠加：

| bug | 表现 | 误导了我多久 |
|---|---|---|
| `-w` 解析错位 | 状态码对、body 错 | 没被发现（碰巧文本响应没事） |
| 分类器顺序 | mp4 判成 html | 一轮 |
| 传截断 url | 必然 403 | **三轮**，误判成「签名有时效」 |

第二个和第三个合起来，正好伪造出一个非常自洽的假象：
「B 站有防盗链 + 地址有时效」。两个假原因互相支撑，看起来完全合理。

**验证脚本本身也要被验证。** 一个自定义的 helper 函数，
在有对照（手工 curl 206）的情况下连续三轮给出 403，那就该怀疑 helper，而不是怀疑网络。

## 十六、三层反向核对（2026-10-21 第 21 轮）

第 20 轮抓到 PiP 缺失，靠的是一条巧劲：**文件在、类型名在，只是协议遵循和回调被摘掉了**。
这轮把这个特征升级成三层系统检查。

### 第 3 层：逐层追下去才知道是不是真缺

追查发现，我方 iOS 的 PiP 与上游是**两套完全不同的架构**：

| | 上游 iOS | 我方 iOS |
|---|---|---|
| 播放器 | `AVPlayerViewController` | `AVPlayerLayer` |
| PiP | `AVPictureInPictureController`（AVKit 托管） | 自建 `PictureInPicture` 类 + 静态 `current` 跨 Duo 折叠保持 |


**结论：不是遗漏，是架构取舍。** 上游用系统渲染换字幕，我方用自绘叠加换 Duo 折叠时的状态连续性
（`PictureInPicture.isActive` 是 static，专门注释说明了为什么）。

登记为架构差异，不进 drop-list（那是我方主动不接的清单，这条是「不同实现路径」）。

### 三层各自的盲区

| 层 | 能抓到 | 抓不到 |

| 文件集合 | 文件被删 | 文件在但内容被掏空 |
| 协议遵循 | 整条协议被摘 | 协议在但方法被删 |
| delegate 方法名 | 方法被删 | 方法在但调用方没挂 |

第 20 轮的 PiP 是**三层都能抓到**的特例（协议、方法、调用全缺）。
真实项目里更常见的是只缺其中一层 —— 所以三层都要跑，且**必须追到调用方**才算定性。

### 问题

| 检查 | 含义 |
|---|---|
| 基线 N > 0 或 = 0 都行 | 现状 |
