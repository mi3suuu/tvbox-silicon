## B2-1 / B2-2 环境隔离（三种实现，三处都对）

| 记录 | 实现 | 位置 |
|---|---|---|
| 订阅 | `subscriptions.filter { environments.shows($0.environmentID) }` | `Store.swift:179` |
| 播放历史 | `playbackHistory.entries(in: environments.activeID)` | `Store.swift:170` |
| 收藏 | `Favorites.items` 计算属性，按 `FavoriteRecord.environment` 过滤 | `Favorites.swift:184` |

**收藏那条差点误判**：grep `environmentID` 时 `favorites` 零命中，看着像漏了。实际是
`FavoriteItem`（身份，`key` 不能被环境污染）× `FavoriteRecord`（环境随身带）两分，`items` 在
`Favorites.swift:184` 里 `records.filter { ($0.environment ?? defaultEnvironmentID) == active }`。
设计比内联字段更稳 —— v2 那种「`[item.key: environment]` 旁挂 map」在同一个剧收藏进两个环境时会塌掉，
v3 才改成每条记录自带环境（`Favorites.swift:151-158` 有注释说明这段历史）。

## B2-3 保险库出口唯一性（查完结论：无风险，附理由）

初查发现 `Store+FullBackup.swift:33` 用**裸数据** `playbackHistory.entries`（全部环境、不剔除）导出备份，
`Store+FullBackup.swift:39` 也是裸 UserDefaults `favorites` 原文。看着像泄露。

**不是泄露**，两个理由：

1. **代码注释明说是设计**：`:31` 写着 `// Playback history (all environments): entries is unfiltered, unlike entries(in:)`。备份按定义要能完整恢复，只导当前环境就恢复不出别的环境。
2. **被隐藏的从来不是收藏/历史**：`PrivacyVault` 只持有 `hiddenSources` / `legacyKeys` / `hiddenSubscriptions`（`PrivacyVault.swift:36/38/42`）——它隐藏的是**源与订阅**，不是收藏条目或历史条目。所以备份的 history/favorites 里本来就不含被隐藏的东西。

**恢复端也没问题**：`restore(_:present:_:)`（`Store+FullBackup.swift:78`）用 `present:` 门控 ——
备份里没有 vault 就跳过，不会拿空值覆盖本地 vault。

> 记一笔方法论：这一项我第一版判成「真泄露」，是因为只看了「裸数据」没读注释、也没看 vault 到底存了什么。
> 属于「判死前没把前提审完」。
