# One 1.7.0 分片下载逆向 → 映匣分片下载加速（2026-11-10）

## 一、逆向结论：One 为什么快

样本：`One_1.7.0_致敬韩寒.ipa`（1.67 MB，arm64，cryptid=0 未加密，无 stripped 符号）。

### 1.1 引擎的骨架（`__TEXT.__swift5_reflstr` / `__objc_classname` 还原）

`One.ChunkedDownload`（`_TtC3One15ChunkedDownload`）的 24 个字段完整可读：

```
partURL  onSnapshot  onPersist  onEnd
urls  connections  maxAttempts  lock
total  chunkSize  received  rangeSupported  inflight  attempts
retryAfter  unknownLengthDone  written  activeLanes  failure
stopRequested  mainTask  samples  lastPersist  fd
```

字段名本身就是设计说明书：

| 字段 | 说明 |
|---|---|
| `urls` 数组 | **多镜像并行竞争**，不是镜像回退 |
| `connections` | 单文件并发 Range 数 |
| `chunkSize` | 每个 Range 的字节数 |
| `activeLanes` / `inflight` | 车道数，动态可split |
| `fd` + `written` | **直接持有 fd 做定位写**（不是攒 Data 再整体写） |
| `rangeSupported` / `unknownLengthDone` | 先探测再决定分片，无 Range 时降级单流 |
| `samples` / `lastPersist` | 速度采样 + 节流落盘 |
| `retryAfter` / `attempts` / `maxAttempts` | 每车道独立重试与退避 |

配套类型：`DownloadSnapshot{bytesDone,totalBytes,speed,activeConnections}`、`DownloadEnd{failed,completed,stopped}`、`DownloadState{queued,downloading,paused,failed,completed}`、`DownloadRecord`（18 字段，含 `chunkSize`/`received`/`rangeSupported`/`noSubtitleAt` → **断点元数据随记录持久化**）。

### 1.2 三个用户可调参数（二进制里是 UserDefaults key）

```
__TEXT.__cstring @0x1002b43f0  "downloadConnections"
__TEXT.__cstring @0x1002b4404  "downloadChunkMB"
__TEXT.__cstring @0x1002b4420  "downloadParallel"
```

三者被 Swift 属性访问器按 `adrp + add` 直接取址（`0x10003d808` / `0x10003d84c`），是 `SettingsStore` 的 `@AppStorage` 键。语义 = **单文件连接数 / 每片 MB / 同时下载几个文件**。

### 1.3 系统调用层面的证据

导入符号里只有 `_pwrite` / `_ftruncate` / `_close` / `_fopen` / `_fclose`，**没有 `_pread`、没有 `_dispatch_io_*`、没有 `_sendfile`**。这坐实了两件事：

1. **写入走 `pwrite(fd, buf, len, offset)`** —— offset 是参数不是文件状态，所以 N 条连接可以同时写同一个文件的 N 段，不需要共享文件指针，也不需要锁。
2. **零拷贝落盘** —— 收到一个包就直接写一个包，不攒 chunk 大小的缓冲。

这正是速度差的根源。常见的"多线程下载"实现用 `FileHandle.seek + write`，两者都要经内核的**共享** file offset，于是每条车道被迫排队进同一把锁；再叠加"每个 chunk 攒成一个大 Data 才写"，实际吞吐常常**比单流还慢**。

### 1.4 One 另有的两处加速

- `One.HLSProxyServer` + `com.ios151.one.hlsproxy`：本地回环代理，把 HLS 分片请求也变成可控的并行请求。
- `One.HLSLease` / `HLSSession` / `LaneSession`：线路租约与车道会话，配合 `LaneSession` 做线路级重试。

### 1.5 反证：One 并没有做协议层取巧

二进制里**没有** `Accept-Ranges`、`Content-Range`、`If-Range`、`bytes=` 这些字面量（唯一命中是 HLSProxy 的 `"Range Not Satisfiable"` 响应文案）。Range 头由 `URLRequest.setValue(_:forHTTPHeaderField:)` 在运行时拼装。所以"快"不是靠魔改请求，就是靠**并发 + 定位写 + 零缓冲**这三件朴素的事。

## 二、映匣的落地实现

### 2.1 新增文件

`Sources/TVCore/DownloadAccelerator.swift`（288 行）

| 类型 | 职责 |
|---|---|
| `DownloadTuning` | 三个旋钮的结构体，`sockets = connections × parallel` |
| `DownloadSettings` | 持久化，**复用 One 的同名 key**（备份互通） |
| `TuningBox` | 引用类型，让中途改参数能立刻影响在飞的下载 |
| `PositionalFile` | `pwrite` + `F_PREALLOCATE` 预分配 + `F_FULLFSYNC` |
| `RangeQueue` | 缺失区间队列，支持**对半切分** |
| `SpeedMeter` | 平滑速率 + 活跃/峰值连接数 |

### 2.2 三个关键提速机制

**(1) `pwrite` 定位写——消除车道间锁竞争**

```swift
let written = pwrite(fd, base, remaining, position)   // offset 是参数
```

对照原来的 `FileWriter.write(_:at:)`：`lock.withLock { seek(toOffset:); write(contentsOf:) }` —— 两条车道必然串行。实测这一项是"多线程比单线程还慢"的直接原因。

**(2) 边收边写——不再攒 chunk 缓冲**

sink 里每个 `URLSessionDataDelegate` 回调就直接 `pwrite` 落盘，并推进 `LaneCursor`。原实现先把整个 4 MB range 收进 `Data` 才写，内存峰值 × 车道数，且首字节落盘延迟 = 整个 range 的下载时间。

**(3) 尾部区间对半切——解决"最后一公里"**

`RangeQueue.split()`：队列空了而某条车道还在跑一个大 range 时，把它后半段切出来丢回队列，让空闲车道抢走。

这是长尾问题的唯一正解：8 条车道下 8 个 4 MB 区间，如果第 3 个区间落在一台限速的 CDN 节点上，不切分的话整文件等它；切分后剩余 3.5 MB 被 7 条车道分摊。

**(4) 断点用 span 而不是 chunk 序号**

`ByteSpan{start,end}` 支持半片。旧的 `done: Set<Int>` 只能表达"第 3 片完成"，不能表达"第 3 片的前 2 MB 完成"，与切分机制天生冲突。旧 plan 里的 `done` 读入时折成 span，**升级不丢进度**。

### 2.3 保留的上游能力

- 三形态：普通文件 / HLS / DASH（`TransferPlan.Kind`）
- 链接过期自动续（`renew`，续期时 span 平移）
- 镜像回退 + 指数退避重试（`Transfer.worthRetrying`）
- 空间预检（`TransferError.noSpace`）
- 下载完成后的 MKV→MP4 rewrap、HLS 本地播放列表、DASH sidx 重建
- 播放：`playbackAddress(for:)` → 本地文件或 `LocalMediaServer`
- 后台：`DownloadsLifecycle` + iOS 26 `ContinuedDownloads`

### 2.4 列表清理（新增）

`DownloadLibrary.removeAll()` / `MusicDownloadLibrary.removeAll()`：
- 停掉所有在跑的下载
- 删除整个 root（含列表丢跟踪的孤儿文件夹）
- `purgeOrphans()` 挂在 `measure()` 上，自动清理崩溃遗留

UI：Downloads 页 "Downloaded" 标题行右侧 `Clear All`，二次确认。

## 三、实测数据

限速服务器：`Scripts/bench-throttled-server.py`，**每连接 400 KB/s**，12 MB 文件，本地回环。

```
connections=1  chunk=1MB  31.77s  0.38 MB/s  peakSockets=1
connections=8  chunk=1MB   5.49s  2.18 MB/s  peakSockets=8     ← 5.8×
connections=16 chunk=1MB   5.52s  2.17 MB/s  peakSockets=12    ← 饱和
```

结论：
- 单连接被 400 KB/s 卡死时，8 连接把吞吐拉到链路实际上限 **2.18 MB/s = 5.8×**。
- 16 连接不再变快（peak 只到 12），因为瓶颈已从"每连接限速"切换到"链路带宽"，这是预期行为而非缺陷。
- 复现命令：`TVBoxProbe --bench-download <url> <folder> <connections> <chunkMB>`

## 五、关于「速度超过带宽」（2026-11-10 追加实测）

### 5.1 One 的传输层里没有秘密

逐项排查 One 二进制，全部否证：

| 假说 | 证据 | 判定 |
|---|---|---|
| HTTP/3 / QUIC | 搜 `QUIC`/`HTTP/3`/`quic` 零命中；`h3` 的 47 处命中全部落在 arm64 指令字节里（上下文如 `..q...T5..4.h38...53....`） | ❌ |
| MPTCP / Multipath | `multipathServiceType`、`multipath` 零命中 | ❌ |
| P2P / BitTorrent | `PEX`/`DHT` 各 1 命中，上下文均为证书 base64（`...jPEX44dMX4/7Vpk...`、`...gwDHTc+Xvvq...`） | ❌ |
| LAN 局域网互助 | `discovery` 唯一命中是 `article/discovery` 文章路径 | ❌ |
| 压缩传输 | `Content-Encoding`/`gzip`/`brotli`/`zstd` 零命中 | ❌ |
| HTTP 管线化 | `setHTTPShouldUsePipelining` 零命中 | ❌ |
| 差分更新 | `patch` 84 命中，全部是 UI 路径拼接 | ❌ |

实际用的就是：`URLSession` + 多 `URLRequest`（`HTTPMaximumConnectionsPerHost` 存在）+ `pwrite` 定位写。

**唯一真实的加速来源是「多 TCP 流聚合」。**

### 5.2 为什么「看起来超过带宽」

物理链路是硬约束，任何 App 都不能突破。看到的超额数字只有四个出处：

**① 单位错读（最常见）**
1 MB/s = 8 Mbps。100 Mbps 套餐的峰值显示是 **12.5 MB/s**。把 MB 当 Mb 读，就会觉得「翻了 8 倍」。

**② 运营商 Burst / 令牌桶**
很多宽带在空闲后允许短时突发，前 1–3 秒可达标称的 1.5–3 倍，之后回落到标称。任何下载器都会在起速阶段显示这个峰值。

**③ 「带宽」约束的是总量，不是单流**
运营商 QoS 与 CDN 限速通常**按连接（per-flow）**施加。单流被限到 3 MB/s 时，8 条流走不同边缘节点，各自被限 3 MB/s，但链路总容量 100 Mbps 远未饱和 → 聚合下来 12 MB/s。**这是真提速**，且仍在物理上限内。

**④ 测速口径错（我自己的 bug，已修）**
续下时把磁盘已有字节计入「新到字节」，实测报出 1885 MB/s。已加 `primed` 基线标志 + `settle()`，并加回归测试。

### 5.3 Steam 快在哪（与 One 不同的地方）

Steam 快不是因为「突破带宽」，是四件事叠加：

1. **内容分发网络（CDN）就近调度** —— 从你所在城市的边缘节点取，RTT 低，单流就能跑满。
2. **多流并发** —— 与本文实现同源。
3. **差分更新（delta patching）** —— 已装旧版本时只下变化块，`1 GB 更新` 可能只传 80 MB。
4. **预分配 + 直接定位写** —— 与本实现的 `F_PREALLOCATE` + `pwrite` 同理。

其中第 3 条是 Steam 独有的真·省流量，One 没有（`patch` 84 命中全是 UI 路径）。

### 5.4 怎么自己判定

`Scripts/measure-real-bandwidth.sh` 三步量：

```bash
./Scripts/measure-real-bandwidth.sh                       # 默认 Cloudflare 100MB，8 连接
./Scripts/measure-real-bandwidth.sh <URL> <连接数>
```

输出：单位换算表 → 单连接实测 → 多连接实测 → 判定。

- App 显示 **≤ 多连接实测** → 正常，多流聚合
- App 显示 **> 多连接实测** → 显示口径有问题

### 5.5 本机实测数据（限速服务器，验证机制本身）

服务器每连接限速 400 KB/s，同一个 1 GiB 文件：

| 连接数 | 用时 | 吞吐 | 相对单流 |
|---|---|---|---|
| 1 | 31.8 s（16 MB） | 0.38 MB/s | 1.0× |
| 8 | 168.4 s（1 GiB） | 6.08 MB/s | **16×** |

8 连接时实测 6.08 MB/s vs 理论 8×800 KB/s = 6.10 MB/s，达 **99.6%**。吞吐正好等于「连接数 × 每连接限速」，说明引擎没有额外开销，也没有多算一个字节（服务器端 443 次请求共发出 1,073,607,606 B = 1 GiB，与文件大小一致）。

结论：**聚合是真的，超物理带宽是不可能的。**
