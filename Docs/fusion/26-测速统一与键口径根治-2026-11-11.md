# 26 · 测速统一 + 源管理「一套状态两套键」根治

日期 2026-11-11 · 分支 `fusion/restructure-A` @ `5a9ff94` + 工作区改动（未提交）

## 一、用户的问题，直接回答

> 我们的测速有多个地方，设置页 / 点播页 / 播放页 / 选集页，这些都测试逻辑都一样吗？还有进步空间控件吗？

**不完全一样。** 四处**共用同一个探针内核** `SourceProbeRunner.probe`（同一个函数、同一套慢启动两段计时、同一套画质解析），
但「喂给它的东西」和「用完写哪儿」这六件事各写各的，实测有 3 处仍在真实分叉。

| 入口 | 走同一内核 | 先解析真实 URL | 传 headers | 廉价预筛 | 读写缓存 | host 闸门 |
|---|---|---|---|---|---|---|
| 设置页 `SourceSpeedTestView` | 是（经批量） | 是 | 是 | 是 | 是 | 是 |
| 点播源 `SourceSpeedLab` | 是（经批量/按范围） | 是 | 是 | 是 | 是 | 是 |
| 选集页 `EpisodePicker` | 是 | 部分是（chip 曾漏） | 是 | 否 | 是 | **唯一原生** |
| 播放页 `OneSkin` | 是 | 是（上游已解析） | 是 | 否 | 否 | 否 |
| 批量扫描 `Store.probe` | 是 | **曾否（已修）** | **曾漏（已修）** | 是（唯一） | 是 | 是 |
| 跨源面板 / 线路矩阵 | 是 | 是 | 是 | 否 | 是 | 否 |

四处不一致的**实际后果**（不是理论风险）：

1. **批量扫描直接拿 `Episode.address` 去测。** 对 type 3/4 源那是 play 参数（`第1集$abc123`），
   而 `URL(string: "abc123")` 会返回**相对 URL 而不是 nil**，所以「地址非 nil 就测」这道过滤一个都拦不住。
   每次都在测一个不存在的地址 → 这类源全部判「不可达」→ 「按测速结果分组」把能用的源归进「不通」。
2. **批量扫描不传 headers。** 要 Referer 的 CDN 对裸请求回 403 → 选集页能播的源，在扫描里是死的。
3. **选集页线路 chip 也拿原始地址测。** 点一下就往缓存写一条 `.unreachable`，还会经 `note` **覆盖掉**
   解析路径刚写好的好读数，污染源测速页、分组与排序。

## 二、根治方式：不是补三处，而是让它不可能再分叉

新增 `Sources/TVCore/ProbePlanTarget.swift` —— **「测什么」的唯一出处**：

```swift
public struct ProbePlanTarget { url, headers, flag }
  .resolve(episode, client:)   // preparePlayback → resolvePlayback，与播放同一条路
  .isRequestable(address)      // 必须 http(s) + 有 host；不认相对 URL
  .defaultFlag                 // 空 flag 归一，写库与显示同一个值
```

三条分叉的**共同点是**：「我要测什么」这件事没有唯一出处。把它收敛成一处之后，调用方只面对
`resolve` 一个函数，就不可能再用错地址、漏 headers、写错键。

配套：`SourceProbeResult.isUsable` 成为**唯一判死出口**。此前 15 处各自写
`reachability != .unreachable`，而它们对 `.unknown` 的处理并不一致（`LineMatrix` 排除、别处放行），
于是同一个源可能在一页「能用」、在另一页「测不到」。

## 三、三个 P0/HIGH：都是「写进去用一套键，读出来用另一套」

这是这个项目源管理里**反复出现的同一类 bug**，本轮坐实三处并根治：

| # | 位置 | 写入键 | 读取键 | 后果 |
|---|---|---|---|---|
| 1 | `Store.reorderSourcesByProbeResult` | `["origin","sourceKey",""]` JSON | 裸 `sourceKey` | **「测速后自动排序」从上线起是空操作**：每次查都 nil → 全部归进 unmeasured → 按原序返回。无报错、无日志，测试也测不出（现有测试用 `keysForTesting` 绕过了键生成器） |
| 2 | `currentSiteListStamp` | 7 个 store 的 revision | 漏 `sourceRouting` / `sourceOverrides` | 改路由、改名后列表继续发旧 `Site`，要等别的戳碰巧变化才生效 |
| 3 | `SiteCard.body` | `sourceOverrides` 存改名 | 读 `site.name` | **改名只在播放器里生效**，卡片上只有一枚「Customized」角标 |

修法：① `reorderByProbe` 的 `score` 闭包改成收 `Site` 而不是 `String` —— 调用方不需要知道内部用什么键，
也就不可能用错一套；② 缓存戳补齐两个 revision；③ 卡片改读 `resolvedSite`。

## 四、新增功能：测完自动整理（Sweep & Tidy）

从前「测速 → 按结果分组 → 按得分排序 → 按可达性改路由」是**四个独立的手动步骤**，
忘一步列表就停在半整理状态。现在串成一次：

```swift
PostSweepTidy: OptionSet { reorder | fileByResult | routeByResult }
standard = [.reorder]
```

- 位置：测速面板新增「测完之后」一节，三个开关。
- **默认只开 `reorder`**：它不移动源、不建组、不改地址。另两项会动用户亲手整理过的东西，得他自己点头。
- 分组只移动**有读数**的源，所以手工整理过的组不会整体抹平。
- 顺序有意：先分组、再路由、最后排序 —— 排序读的应该是移动之后的状态。

## 八、虚拟流也能测（用户追问后修正）

第一版把 `tvbox-cloud://` / `tvbox-hongguo://` / `tvbox-dash://` 当作「测不了，跳过」。
用户否决：**这三类也要能测**。已改为真正支持。

它们不是「神秘地址」，只是「给我某个文件的第 N..M 字节」——
而这正好就是 `WebCastVirtualStreams` 已经做好的抽象（网页投射用它把三类地址变成 HTTP 字节流）。
测速直接复用同一个口：

```swift
SourceProbeRunner.probe
  ├─ WebCastVirtualStreams.source(for: url)  → .cloud / .hongguo / .playlist
  │    并且用**和 HTTP 那条路完全相同的两段计时**（前 warmupBytes 打时间戳，后段算稳态）
  ├─ scheme 是三兄弟但解析不出流      → .unknown（没测出来）
  └─ 其余                             → 普通 HTTP 请求
```

两个关键判断：

1. **口径必须一致。** 同一个源在「选集页（HTTP 直测）」和「扫描（虚拟流）」里若用两套计时，
   就会给出两个数字 —— 那比测不了更糟。所以虚拟流路径照抄了 `warmupBytes` 的稳态算法，
   不复用 `stream(_:session:budget:)`（它吃 `URLRequest`），但算法同源。
2. **解析不出流 ≠ 判死。** 流还没注册、或注册已被回收时，落回 `URLRequest` 会必然失败并被记成
   `.unreachable` —— 那就把一个能播的源送进了「不通」分组。现在显式返回 `.unknown`（没测出来）。
   这条是被测试逼出来的：`virtualStreamAddressesAreMeasurableThroughTheirOwnReader` 第一次跑就红。

## 九、复核子代理复查出的 3 项必修（已全部修掉）

| 严重度 | 问题 | 修法 |
